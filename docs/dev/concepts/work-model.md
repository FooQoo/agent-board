# The work model in code

The [work model](../../guide/work-model.md) is the set of rules that tell an agent what to do next, when it is finished, and when to stop and ask. This page shows where each rule is enforced in the code and which tests cover it, and where the model leaves a gap that relies on the agent instead. Read it before you change a rule, so that you know which code and which tests move with it.

Every path is relative to the repository root. The rules are enforced in `FileStore` operations that run under the project's write lock, so the CLI, the web server, and the watcher all pass through the same checks. For the rules in the user's words, see [What Agent Board guarantees](../../guide/work-model.md#what-agent-board-guarantees). For the surrounding mechanics, see [Tasks and states](./tasks-and-states.md), [History and decisions](./history-and-decisions.md), [Saving and recovery](./saving-and-recovery.md), and [Agent integration](./agents.md).

## How a rule is enforced

A write goes through one path. The operation takes the project lock (`lock_project` in `src/file_store/ops/mod.rs`), reads the task strictly (`read_task_strict` in `src/file_store/reader/task.rs`), checks the rule, and saves the task and its history together. A rule that is only a convention in the agent's Skill is not on this path; the second table below lists those.

Whether a task waits for you is not stored. `QaIndex::is_waiting` in `src/file_store/qa/store.rs` derives it from the questions the task refers to, and `task_waits` in `src/file_store/ops/qa/mod.rs` reads the latest files for it under the lock. The Pending state, the refusal to run, and the refusal to finish all come from that one derivation.

## What Agent Board guarantees

Each row is one rule from the guide. The tests named are the ones that exercise the rule directly. A rule with no direct test says so.

| Rule | Enforced in | Tested by |
| --- | --- | --- |
| The owner of a task never changes. | `create_task` in `src/file_store/ops/task/create.rs` is the only place that sets the owner. The edit operations in `src/file_store/ops/task/edit.rs` take no owner. | No direct test. The missing owner argument is the guard. |
| Only valid states exist. | `check_work_state` in `src/domain/mod.rs`, called from `set_agent_status` in `src/file_store/ops/agent.rs`. It returns `InvalidStateForAssignee`. | `run_states_follow_the_table_for_each_owner_and_column` in `tests/domain_work.rs`; `running_on_a_human_task_in_doing_is_refused` and `running_on_a_done_task_is_refused_by_the_state_table` in `tests/file_store_agent.rs`. |
| Nobody can set Pending by hand. | `set_agent_status` in `src/file_store/ops/agent.rs` refuses `Pending` before it reads the task. | A request for `pending` to the agent-status route is refused with 422 in `tests/server.rs`. No file-store test. |
| The agent waits while a question is open. | `set_agent_status` refuses `Running` with `QuestionsUnanswered` when `task_waits` is true. | `running_is_refused_while_a_referenced_question_is_open` in `tests/file_store_agent.rs`. |
| Asking a question puts a Running task back to Idle. | The ask operation in `src/file_store/ops/qa/ask.rs` sets Idle and adds a history entry in the same batch that saves the request. | `one_request_holds_several_questions_with_their_own_numbers_and_tasks` in `tests/file_store_qa.rs` checks the task is Pending and then Idle. |
| A planned task stays Pending until the start is approved. | `QaIndex::is_waiting`: a task that refers to a plan question that is not withdrawn waits until it refers to an approved start approval (`is_given_approval` in `src/file_store/qa/model.rs`). An approval that was not given blocks too (`is_rejected_approval`). | `an_answered_plan_question_keeps_the_task_waiting_until_an_approval_is_given`, `a_refused_approval_keeps_a_plan_task_waiting`, `a_rejected_start_approval_keeps_the_task_waiting_until_it_is_unlinked`, and `a_withdrawn_plan_question_does_not_hold_the_task` in `tests/file_store_qa.rs`. |
| An answer is recorded once, and saved with the history. | `answer_questions` in `src/file_store/ops/qa/answer.rs` refuses a question that already has an answer. It saves the request and the history of the referring tasks with `save_batch_locked` in `src/file_store/transaction/batch.rs`. Asking and withdrawing use the same batch. | `the_first_answer_is_kept_and_a_conflicting_batch_writes_nothing` in `tests/file_store_qa.rs`; `tests/file_store_transaction.rs` for the paired and batched saves. |
| An AI-owned task is Done only when its conditions are met. | `auto_complete_project` in `src/file_store/ops/completion.rs` requires at least one condition, all done, no waiting, no draft, no archive, and a task in Todo or Doing. It reads the files again under the lock before it moves the task, and writes a lane entry with a reason. | `only_valid_nonempty_fully_done_ai_conditions_are_eligible`, `completed_ai_todo_moves_once_and_records_a_reasoned_lane_event`, and `pending_is_left_alone_then_answered_task_is_reconsidered` in `src/file_store/ops/completion/tests.rs`. |
| A manual move to Done by an agent needs the same. | `move_task` in `src/file_store/ops/agent.rs` calls `ensure_acceptance_met` and `task_waits` when the agent moves a task to Done. It returns `AcceptanceUnmet` or `QuestionsUnanswered`. | `an_agent_cannot_move_a_task_to_done_while_a_condition_is_unmet` in `tests/acceptance_cli.rs`. No direct test for the open-question refusal on a manual move. |
| Finished work stays finished. | `ensure_ai_task_not_done` in `src/file_store/ops/mod.rs` refuses the agent on a Done task. `auto_complete_project` looks only at Todo and Doing, so unchecking a condition does not reopen a Done task. | `done_tasks_reject_agent_edits_but_a_person_can_reopen_them` in `tests/file_store_agent.rs`; `direct_task_file_updates_are_rechecked_and_existing_done_is_not_reopened` in `src/file_store/ops/completion/tests.rs`. |
| Drafts are fenced off from agents. | `TaskIsDraft` is returned by the agent move and state code in `src/file_store/ops/agent.rs`, by `src/file_store/ops/task/edit.rs`, and by `src/file_store/ops/qa/ask.rs` and `link.rs`. | `a_draft_task_refuses_agent_moves_and_accepts_user_moves` in `tests/file_store_agent.rs`; `a_draft_refuses_agent_edits_and_its_files_stay_unchanged` in `tests/file_store_task.rs`; `a_draft_refuses_edit_mv_and_state_and_changes_and_announces_nothing` in `tests/cli_agent_board.rs`. |
| Nobody writes to an archived task. | Each write operation returns `TaskArchived` first: `src/file_store/ops/agent.rs`, `src/file_store/ops/task/edit.rs`, `src/file_store/ops/task/acceptance.rs`, `src/file_store/ops/task.rs`, `src/file_store/ops/qa/ask.rs`, and `link.rs`. | The refusal is checked for edits in `tests/file_store_task.rs`, for the condition toggle in `tests/acceptance_toggle.rs`, and for epic changes in `tests/file_store_epic.rs`. No test covers every operation. |
| Changes leave a reason in the history. | `transition_event` in `src/file_store/ops/history_event.rs` builds the entry for lane, state, draft, epic, archive, and condition changes. The question and answer entries are built in `src/file_store/ops/qa/`. | `a_running_and_idle_task_in_doing_keeps_its_lane_and_records_each_reason` in `tests/file_store_agent.rs`; `tests/history_cli.rs`. |
| Numbers are never reused. | `nextTaskId` in `project.json` is reserved before the task folder is written (`create_task`). Question numbers come from `next_question_id` in `src/file_store/ops/qa/ask.rs`. | `task_numbers_are_not_reused_after_a_delete` in `tests/file_store_task.rs`. No direct test for question numbers. |
| A broken record is not guessed at. | `read_task_strict` in `src/file_store/reader/task.rs` and `compose_task` in `src/file_store/history.rs` return `FileInvalid` for a history entry that is not exactly a time and a reason. | `stored_history_requires_only_valid_at_and_nonblank_reason` and `invalid_history_field_types_and_timestamps_have_precise_paths` in `tests/file_store_history.rs`; `writing_to_a_task_with_a_broken_task_file_is_refused` in `tests/file_store_task.rs`; `cli_edit_refuses_invalid_history_without_rewriting_task_markdown` in `tests/history_edit.rs`. |
| Rewriting a plan keeps the history and the links. | `write_text` in `src/file_store/ops/text.rs` replaces only the body and the conditions, and keeps the stored `history` and `questions`. A `history` or `questions` written in the input is ignored. | `edit_with_desc_file_keeps_question_refs_and_the_task_stays_pending` in `tests/cli_qa.rs`; `cli_file_replacement_without_history_keeps_current_history` in `tests/history_edit.rs`. |

## What still relies on the agent

Each row is a path that lets the item through. The [guide](../../guide/work-model.md#relies-on-agent) tells the user what to expect. This table explains why the code does not stop it.

| Item | Why it is not enforced | Where |
| --- | --- | --- |
| Before a plan is linked to a question. | A task is created Idle in Todo, and `is_waiting` is false while the task refers to no question. The plan's questions are linked in a separate step, so another agent can take the task in between. | `create_task` in `src/file_store/ops/task/create.rs`; `QaIndex::is_waiting` in `src/file_store/qa/store.rs`. |
| A task reused in a new plan. | `is_waiting` accepts any approved start approval linked to the task. A task that still refers to an approval from an earlier plan satisfies it, so once the new plan question is answered the task stops waiting, although the new plan was not approved. | `QaIndex::is_waiting` in `src/file_store/qa/store.rs`; `is_given_approval` in `src/file_store/qa/model.rs`. |
| Withdrawing a question. | `withdraw_request` receives an `Actor` and ignores it (the parameter is `_actor`), and the CLI accepts both actors. An agent can withdraw a request and release the wait. | `src/file_store/ops/qa/withdraw.rs`; `QaWithdrawArgs` in `src/cli/args/qa.rs`. |
| Tasks with no conditions. | `ensure_acceptance_met` passes when the list is empty, so an agent can move such a task to Done by hand. Automatic Done requires at least one condition. | `ensure_acceptance_met` in `src/file_store/ops/agent.rs`; `auto_complete_project` in `src/file_store/ops/completion.rs`. |
| Who answered. | `answer_questions` records the answer and the channel (`--via`), but the command takes `--actor human` on trust. An agent that relays a chat reply writes it on the user's behalf. | `src/file_store/ops/qa/answer.rs`; `HumanActorArg` in `src/cli/args/qa.rs`. |
| Editing the files directly. | The checks live in `FileStore` operations, and a write to `TASK.md` by another program does not call them. The watcher re-reads the file and may run automatic Done, but it adds no history for the edit and refuses nothing for a draft, Done, or archived task. | `src/file_store/watch.rs`; [Saving and recovery](./saving-and-recovery.md#when-files-are-invalid). |
| Running. | `Running` is stored as reported. Nothing expires it or checks that the agent is alive. | `set_agent_status` in `src/file_store/ops/agent.rs`. |
| Automatic Done needs the server. | `auto_complete_project` runs from the file watcher and at the server's start, not from the CLI. A task that becomes eligible while no server runs waits until the next start. | `src/file_store/watch.rs`; `auto_complete_all` in `src/file_store/ops/completion.rs`. |
| Your own tasks. | A person's task can only be Idle, and automatic Done skips it. Moving it to Done and checking its conditions are recorded, not verified: `ensure_acceptance_met` is called only for an agent's move. | `check_work_state` in `src/domain/mod.rs`; `move_task` in `src/file_store/ops/agent.rs`. |
| Epics. | An epic has no managed acceptance conditions and no completion state. Its completion conditions are Markdown in `EPIC.md`. | [Tasks and states](./tasks-and-states.md#epics-and-priority). |

## Where the agent's part is written down

The agent's side of these rules is the Skill, not code: registering a plan before linking its questions, calling you only in four cases, and recording history. See [Agent integration](./agents.md). A change that moves a rule from the Skill into the code belongs in the first table above, and a change that adds a rule to the Skill belongs in the second.
