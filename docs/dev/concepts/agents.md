# Agent integration

Agents use Agent Board through three pieces: the skill that tells them how to work, the hook that hands them the progress table, and the waiting commands that let them block until the project changes or a person answers. This page explains each piece and how `agboard setup` installs them as the Agent Board plugin. The user-facing workflow is in [Working with agents](../../guide/delegate/agents.md); the JSON they receive is in [Hook, progress, and wait output](../reference/agent-output.md).

## How the pieces fit together

| Piece | Lives in | Job |
| --- | --- | --- |
| Skill `agent-board` | `src/skills/agent-board.md` and `src/skills/topics/`, printed by `agboard skills`; the plugin's `SKILL.md` only runs that command | Judgment: how to choose work, report progress, ask decisions, and respect drafts and Done tasks. |
| Skill `remote` | `plugins/agent-board/skills/remote/SKILL.md` | Hands the user the phone address and passcode from `agboard --project "<name>" show remote --json`; starts nothing. |
| Skill `wait` | `plugins/agent-board/skills/wait/SKILL.md` | Keeps a session listening: follows `agboard skills resident` with a 3600-second default timeout and restarts the wait after `idle_timeout`. |
| Hook | `agboard hook` (`src/agent/hook.rs`) | Fetching and formatting: after tool calls, attach the current progress table to the agent's context. |
| Progress table | `src/progress.rs` | The list of workable tasks, shared by `agboard progress` and the hook. |
| `wait` | `src/agent/wait.rs`, `src/agent/task_wait.rs` | Block until the project changes or the next task is ready. |
| `message ask`, `message wait` | `src/cli/commands/message/`, `src/agent/message_wait.rs` | Ask the user questions and block until none of them is open. |

The skill is named `agent-board`; the executable is `agboard`. A typical loop: the hook shows the progress table → the agent reads only the `EPIC.md` and `TASK.md` it needs → it clarifies an unclear title through `agboard edit --title`, preserving the original request → it moves the task to Doing and Running → it records progress with `history add` → it asks questions with `message ask` and waits for the answers when blocked → it checks conditions off, and automatic Done finishes the task. Title refinement is a skill instruction shared by the ordinary loop and listener, not a server-side summarization feature.

Agents append progress at the start, meaningful progress, decisions, verification, interruptions, and resumptions, without per-entry approval, and never duplicate entries that operations already appended. The body keeps the plan and concise verification results. Images can be attached when visual proof is useful.

The skill gives `BUG` and `ENHANCEMENT` a fixed-body exception: they are ongoing classification epics, not per-feature plans. Their canonical bodies are the topics `bug-epic-template` and `enhancement-epic-template` of `agboard skills`. After one-time initialization in the board’s language, normal work and listener runs record plans and outcomes only on tasks. An explicit user request is required to replace existing non-empty content, with useful old content retained in relevant task bodies. The `waves` frontmatter remains editable. This is not a server-side edit restriction.

## The progress table and the hook

The progress table lists Todo and Doing tasks that do not wait for a person, grouped by epic in `waves` order, with each task's ID, title, owner, status, acceptance counts, and the paths of its `EPIC.md` and `TASK.md`. It never includes bodies or history. `nextTasks` (`next_tasks` in `src/progress.rs`) names up to three AI tasks to pick up now, so ready work does not hide among tasks that are running or yours: Doing and Idle tasks (`resume`) first, then Todo and Idle tasks (`next_in_epic`), in the order `ordered_tasks` gives. A Todo task is held back while a task of an earlier wave of its epic is not Done (archived tasks are ignored); `resume` work is never held back. It does not evaluate other dependencies, which are prose in `EPIC.md`. A waiting task higher in the order does not block lower tasks, and a task whose questions are answered returns to the table while it is unfinished. The `pending` section's `question` is the first 200 characters of the open question with the smallest ID.

`src/progress.rs` builds the optional `pending` and `done` sections from `Include`, which `agboard progress` and `agboard hook` fill from `--include-pending` and `--include-done`. The default `Include` adds nothing, so the default table is unchanged. See [Epics and progress](../../guide/watch/epics.md#read-the-progress-table) for the options.

The hook identifies the project from the nearest bound ancestor of the input `cwd` (or the process cwd), never from a session ID, and never selects all projects when the folder is unbound, and never falls back to a parent when the nearest binding is broken. The table carries the board's saved language as a top-level `locale` when it is not English, read straight from `preferences.json` (`saved_locale` in `src/server/preferences/`), as a hint that keeps replies in the user's language. It returns the table as `AGBOARD_PROGRESS` JSON in `hookSpecificOutput.additionalContext`, or an `AGBOARD_ERROR` such as `bound_project_missing`. A folder with no binding at all is not an error; see [Hook skip and errors](#hook-skip-and-errors).

- **Claude Code.** The plugin's `hooks/claude.json` registers `agboard hook --agent claude` on SessionStart (`startup`, `resume`, `clear`, and `compact`), PostToolUse, PostToolUseFailure, and Stop, without a fixed project name. Generic skill frontmatter hooks are not used.
- **Codex.** The plugin's `hooks/codex.json` registers `agboard hook --agent codex` on SessionStart, PostToolUse, and Stop. Codex runs a plugin's hooks only once they are trusted; `agboard setup` and `agboard update` trust them (see [Setup and update](#setup-and-update)).
- **Limits.** The table is limited to 256 KiB and a run to 10 seconds. Codex's `additionalContextLimit` is set to 0 so the hook enforces its own limit. Exceeding it reports `context_too_large`; output is never truncated and reported as success. When the table cannot be produced or the input cannot be read, the hook says so and keeps the original tool result.
- **Input.** The hook reads its input to the end, whatever its size, and takes only `hook_event_name` and `cwd` from it (and, on Stop, `stop_hook_active`, `last_assistant_message`, and `transcript_path`). The agent sends the whole tool result with every PostToolUse, so the input is large after an image read or a long command output; the tool input and result are skipped, never kept or passed on.
- **Stop.** At the end of a turn, the hook runs the rules of the nudge registry that apply at the turn end (`src/nudge/`, see [Nudge rules](#nudge-rules)) and, when they give any reminder, blocks the turn once with a checklist as the reason (`{"decision":"block","reason":"..."}`; the code is in `src/agent/stop/`). A reminder is either **Definite**, a violation the hook verified, or **Check**, a trigger that fired for the agent to judge. The reason starts with a short header, then a `Found:` section with `- NG: ...` lines for the definite reminders and a `Check:` section with `- [ ] ...` lines for the checks; an empty section is left out, and with no reminder the turn ends as usual. The rules see the Stop input, the turn read from the transcript (the last reply and the tool calls with their command text), and the bound project's progress table, computed in process. The hook does nothing when `stop_hook_active` is true (so it blocks at most once), when the folder is bound to no project, when a rule's data cannot be read, or on any error. The turn starts at the last real user message for Claude Code, and at the `task_started` event of the input's `turn_id` for Codex (else the last one), because Codex also records injected context as user messages. The last 8 MiB of the transcript are read, and Codex `function_call`, `local_shell_call`, and `custom_tool_call` entries count as tool calls (`src/nudge/turn.rs`). The reply comes from `last_assistant_message`, else from the transcript. The transcript can lag the turn, so an `agboard` call made at the very end may be missed once; the block then costs one extra turn.
- **Safety.** Commands are fixed; nothing is built from task text or `tool_input`. The hook never calls agent tools, never triggers itself, and changes no board file. When it adds a progress table, it starts the server in the background if none runs, without waiting, unless `agboard stop` paused that or `AGBOARD_AUTOSTART=0` is set (see [Server and web UI](./server-and-ui.md#how-a-command-starts-a-server)). This keeps automatic Done working while an agent only edits files. A server started this way opens the board of that project in the browser once (see [Opening the board](./server-and-ui.md#opening-the-board)). Paths appear only in local CLI and hook output, never in remote JSON.

Agents make no board-dependent changes until the table can be read, and they read a fresh table after context compaction.

The skill puts every question on the board as a project question with choices, asked with `message ask`. During a conversation the agent also writes the same question in the chat as plain text, with the choice ids and labels and its recommendation, and never opens the agent's own question tool: a tool call that stays open blocks the agent, so it could not notice an answer given on the board, and a dismissed tool call reads as a refusal. It writes a chat answer back with `message answer --actor human --via chat`, using the user's own words, and does not record it again when the waiting command then ends with `answered`. When the board already holds an answer, `question_answered` returns it; the agent continues with that answer, tells the user which one was recorded, and never asks the same question again in the other channel. The skill also tells the agent to write chat replies in the language the user speaks with it, as it does for board content. The skill uses `--no-wait` only when the user explicitly asks to register a question and return immediately (or in a session the board launched, see below), and never asks only in the chat when the board is unavailable.

The skill turns a multi-task request into a provisional plan: it registers the epic and the tasks first, asks any questions the plan needs with `message ask`, and revises the plan from the answers. The epic and tasks an agent creates are AI drafts, so `wait --until task` and the work loop do not pick them up until they are started (see [Drafts](./tasks-and-states.md#drafts)). When the questions are answered and the plan is written up, the agent starts the plan itself with `agboard epic start <EPIC-ID> --actor ai` (or `agboard start <id> --actor ai` for one task); an open question linked to the task (or to an AI draft of the epic) refuses the start with `start_blocked_by_questions`. Then the agent works in the epic's order and calls the user only for unclear intent, preference, irreversible actions, and growing scope. This is a skill instruction; apart from the derived Pending state, the CLI and the server do not enforce it. See [Break a request into tasks](../../guide/delegate/agents.md#break-a-request-into-tasks) for what the user sees.

In a session a person started, the skill waits the same way in every agent: it keeps `message ask` running until its last line, and after `timeout` runs `message wait <question-id>`. Claude Code runs the command in the background, is told when it ends, and ends its turn after showing the question, so an answer on the board wakes it; Codex cannot be woken that way, so it runs the command in the foreground and reads its output in chunks without a time limit on the command, and the user answers on the board or interrupts it to reply in the chat. The default 600-second wait matches the 10-minute limit of a Claude Code tool call. Nothing pushes an answer into such a session (a session the board launched is the exception: it asks with `--no-wait` and the answer is pushed to it, see [Push mode](#push-mode)): the board only stores answers, and the command that waits returns them.

### Nudge rules {#nudge-rules}

A nudge reminds an agent of something it tends to forget. One registry, `RULES` in `src/nudge/rules.rs`, feeds both places an agent is reminded: the `reminders` of the [progress table](../reference/agent-output.md#progress-table) while it works, and the Stop hook's checklist at the end of a turn. A rule is one entry with these fields:

| Field | Values |
| --- | --- |
| `id` | A stable kebab-case name. It is the `rule` of every reminder the rule gives. |
| `area` | What the rule is about: `Question`, `Record`, `Acceptance`, `RunState`, or `Epic`. |
| `source` | `State` reads the progress table only; `Turn` also reads the turn (the reply and the tool calls). A `State` rule never sees the turn, so it gives the same result in the table and in the hook. |
| `when` | `Working` shows it in the progress table, `TurnEnd` in the Stop checklist, `Both` in both. Only a `State` rule can be shown while the agent works. |
| `kind` | `Definite` for a violation the rule verified, `Check` for a trigger the agent judges. |
| `check` | A function over `Facts` (the progress table, the optional turn, the reply, and the clock) that returns zero or more `Finding`s: a text and, when it applies, a `task_id`, `message_id`, or `epic_id`. |

The rules:

  - **`question`** (Turn, TurnEnd, Check). Triggers when the last non-empty line of the reply ends with `?` or `？` (closing quotes, brackets, and Markdown emphasis are ignored) and no tool call of the turn ran `agboard ... message ask` or `message answer`. It gives two reminders: does the question wait on the user's answer (then put it on the board with `message ask` and show it in the chat), and does it ask about something visual (then attach the images).
  - **`question-images`** (Turn, TurnEnd, Check). The turn produced an image (the detection of `result-artifact`) and ran `agboard ... message ask` with no image: no `images` in the questions JSON, no `attachment:` reference, and no `agboard attachment add` in the turn. It asks for the images to be attached when the question is about something visual.
  - **`question-in-chat`** (Turn, TurnEnd, Definite). The turn ran a real `message ask` (not `--help`) but the last reply holds no `Q-<n>` reference. It asks to show the question with its Q-id in the chat too. It stays silent when the reply cannot be read.
  - **`question-wait`** (Turn, TurnEnd, Definite). The turn ran `message ask ... --no-wait` and no `agboard message wait` followed it. It asks to wait with `agboard message wait <Q-id>` in the background, or to explain why not.
  - **`final-result`** (State, Both, Definite). A task listed in `finalResultMissing` gives a reminder naming it and asking for `result add <id> --final`.
  - **`answer`** (State, Both, Definite). Each entry of `answers` gives a reminder naming the question: read it with `message show`, act on it, and run `message accept`.
  - **`request`** (State, Both, Definite). Each entry of `requests` gives a reminder: read it with `message show`, accept it with `message accept`, and plan it.
  - **`conditions`** (State, Both, Check). An AI task in Doing has a recorded `--final` result but fewer acceptance conditions done than it has: record the verification and set the conditions done in `TASK.md`.
  - **`epic-close`** (State, Both, Definite). An entry of `epicsToClose` (an epic other than `BUG` and `ENHANCEMENT` with at least one task, all of them Done, whose `EPIC.md` body still has an unchecked `- [ ]`): verify the reference conditions and record the outcome.
  - **`stale-running`** (State, Both, Check). An AI task is Running and its latest history entry (or its last run-state change when it has none) is older than 30 minutes (`STALE_RUNNING_MINUTES` in `src/nudge/state_rules.rs`): set it back to idle with `state` if the work stopped, or record progress with `history add`.
  - **`next-task`** (State, Both, Check). `nextTasks` is not empty and no AI task is Running: pick up the first next task.
  - **`draft-moved`** (State, Both, Definite). An AI draft is in Doing, so a person moved it there: start it with `start <id> --actor ai`.
  - **`drafts`** (State, Both, Check). An AI draft with no open question (a draft with one waits and is not listed). One reminder per draft, with its id, title, and lane: a draft means its plan is not settled. If the plan is settled, start it (put its order in the epic priority and dependencies in `EPIC.md`; do not leave it as a draft to make it wait). If not, ask the question that settles it.
  - **`result-pr`** (Turn, TurnEnd, Definite). The project has an AI task in Doing and Running, the turn ran no `agboard ... result add`, and it ran `gh pr create`: a pull request was opened with no result.
  - **`result-artifact`** (Turn, TurnEnd, Check). The same conditions with no `gh pr create`, but a `git push` or an image written (an image file with `.png`, `.jpg`, `.jpeg`, `.gif`, or `.webp`, or a screenshot): record it with `result add` if the requester can look at it.
  - **`history`** (Turn, TurnEnd, Check). The project has an AI task in Doing and Running, and the turn made a commit, ran tests (`cargo test`, `pnpm ... test`, `npm test`, `vitest`, `playwright test`, and the like), pushed, or opened a pull request, with no `agboard ... history add`, `state`, `mv`, or `result add`. It asks for meaningful progress to be recorded with `history add`.
  - **`conditions-after-merge`** (Turn, TurnEnd, Check). The turn ran `gh pr merge` and an AI task in Doing has conditions that are not done. It names each such task and asks the agent to record the verification in the task body and set its conditions done once the merge verified the work (a pull request is not linked to a task, so the agent decides which).
  - **`start-task`** (Turn, TurnEnd, Definite). The turn edited files (an Edit or Write call with a path, `apply_patch`, or `git commit`) and no AI task is in Doing and Running. Edits only under `/tmp` or the Agent Board data folder are ignored. It asks the agent to start the task (`agboard mv <id> doing`, `agboard state <id> running`) or create one.

#### Add a rule

1. Add a function `fn(&Facts) -> Vec<Finding>` and an entry to `RULES` in `src/nudge/rules.rs`, with the fields above. Keep the list in the order the reminders should appear.
2. Add cases to `src/nudge/cases.rs`: at least one where the rule triggers and one where it does not. `every_rule_has_cases` fails without both, and `every_case_gives_the_expected_result` runs them all.
3. Add the rule to the list above, here and in the Japanese page. A test fails when a rule id is missing from either.
4. If the rule belongs to a command or a progress field, replace its `NoRule` in `src/nudge/coverage.rs` with `Rules(&["your-rule"])`.

A `State` rule needs no change elsewhere: its reminders appear in the progress table (and so in the hook's context) and in the Stop checklist by themselves. A `Turn` rule that needs a new fact about the turn extends `src/nudge/turn.rs`, which reads both transcript formats.

#### When you add a feature

Every `agboard` command and every top-level field of the progress table is listed in `src/nudge/coverage.rs`, mapped to the rules that watch what it creates or to `NoRule("reason")`. The tests derive both lists from the code (the clap command definition and the serialized progress table), so adding a command or a field fails them until you decide: does the new feature create something an agent could forget, such as a question to ask, a record to write, or a state to leave right? If it does, add a rule as above. If it does not, record `NoRule` with the reason. A reason of the form `planned: #NNN` names the task that adds the rule.

## Waiting for changes

`agboard wait --after <cursor>` blocks until the project changes:

1. Read `pid` and `port` from `serve.json` in the same data area and connect to `GET /api/events`. When no server answers, start one first and wait until it does (see [Server and web UI](./server-and-ui.md#how-a-command-starts-a-server)). If the connection fails after `serve.json` was read, start a server once more.
2. Match the project name against the cursor and fix the ProjectId. A cursor for another project, or in an old format, is `cursor_invalid`.
3. After `ready`, compare the project's current version with the cursor. If they differ, return at once; this catches changes made between fetching and subscribing.
4. Otherwise wait for `changed`. If a re-read shows the same version (another project changed), keep waiting.

- `changed`, `ready`, and keep-alive comments are distinguished. Renames return the same project's snapshot; deletion returns `project_not_found` and never moves to a re-created project.
- The connection limit is 3 seconds, and the wait itself is unlimited by default. With an optional `--timeout`, it checks the version once more at the end and returns `wait_timeout` if nothing changed. A disconnect during the wait returns `board_unavailable`; the wait does not start a server again then. There are no automatic short retries and no periodic polling.
- A change wait does not trust one read of a file that differs from its cursor: an editor saving in place truncates the file before it writes it, so a read can land in the middle. The wait reads again after 250 ms, never past its deadline, and returns only if the change is still there. A save that restores the same content wakes nothing; a real change is returned about 250 ms later.
- Disconnects, timeouts, and Ctrl+C never change tasks or history, never count as "no change", and never restart a finished agent.
- Because CLI notifications are best effort, a missed one is caught on the next connection, a real `changed`, or the final read at a timeout.

### Waiting for answers

`message ask` saves the questions, notifies `serve`, and then waits for their answers on the same SSE stream (`src/agent/message_wait.rs` on top of `wait_engine`). A preflight check runs before the save and starts the server when none runs (see [Server and web UI](./server-and-ui.md#how-a-command-starts-a-server)), so a server that cannot start stores nothing and fails with `board_unavailable`. `message wait <question-id> [<question-id>...]` waits again for questions that are already stored and never asks a second time.

The output is JSON Lines with `--json`, or the same events as English sentences without it. The first line is `registered`; the last is `answered` (exit 0), `timeout` (exit 5), `withdrawn` (exit 6), or `error`. In between, `waiting` lines come every `--heartbeat` seconds (default 60, 10 to 600). The heartbeat is a timer and never reads the board; the board is read only when the server reports a change. `answered` comes only when every question is answered. When no question is open any more but some were withdrawn, the command ends with `withdrawn` instead. The wait lasts 600 seconds by default; `--timeout` takes 1 to 86,400 seconds, or `none` for no limit. A timeout, interruption, or lost connection leaves the questions open. `--no-wait` prints `registered` after saving and notifying and needs no server.

Asking returns a Running task to Idle. After the answers arrive, the agent reads them and the history, then explicitly resumes Running with a reason. The event fields are in [Agent output](../reference/agent-output.md#message-events). See [Decision requests](../../guide/delegate/decisions.md) for the user workflow.

### Waiting for the next task

`agboard --project <name> wait --until task --idle-timeout <seconds> --json` uses the same event-driven wait engine. It reads eligible tasks immediately before subscribing, checks again after the SSE `ready`, and checks after each `changed` event. A single monotonic deadline starts when the initial snapshot has no eligible task; unrelated project changes and keep-alives do not extend it. At the deadline it reads once more, returning a task if one arrived at the boundary, otherwise `idle_timeout` with exit code 0.

The selector uses `ordered_tasks`, the same ordering as the progress table: epics sorted by ID, each epic's saved waves and then task ID, followed by ungrouped tasks by ID. It returns one AI-owned Todo or Doing task whose shown run state is Idle (a task that waits for a person shows Pending and is never returned), provided it is not a draft or archived. A Todo task of an epic with waves is skipped while a task of an earlier wave is not Done (`gated_by_waves`, shared with `nextTasks`); an idle task in Doing is still returned. The initial read means tasks created before listening are eligible. Before any task, the selector returns the answers that no agent has taken in and the open requests (see below). The result contains the snapshot cursor, the task, its local `TASK.md` path, and its `EPIC.md` path when it has an epic. Selection is read-only and does not claim a task; callers must re-read its state before acting. The listener procedure checks the complete snapshot first and resolves any existing AI work in `running` or `pending`; an idle task in Doing is eligible to resume. A timeout is a normal idle result, while a read defect, unavailable server, or deleted project remains an error.

A person's answer to an agent's question reaches the agent in the same three places, in an `answers` array and an `answers` result (see [Agent output](../reference/agent-output.md#progress-table)). An answer waits until an agent takes it in with `message accept`, which records `acceptedAt` in the reply. `message ask` and `message wait` take in the answers they return, and an answer an agent records from the chat is written already accepted, so an explicit `message accept` is needed only for an answer seen through the hook, the table, or `wait --until task`. An answered question that waits for acceptance does not make a task Pending, and a changed answer wakes a listening agent like a request does. The wait returns answers first, then requests, then tasks.

A person's request reaches an agent in three places: the `requests` array of the progress table, the same table in the hook, and the `requests` result of `wait --until task`. A request is open until an agent accepts it with `message accept` or the person withdraws it. A new, accepted, or withdrawn request changes the project's `messages` resource, so a listening agent wakes on the same `changed` event as for a new task. The wait returns open requests before tasks and returns the same ones again until one is accepted; accepting is explicit, so a request is never taken because a wait returned it. An open request does not make any task Pending: only an open question or an unreadable message file does.

For one-session orchestration, the listener procedure (`agboard skills listening`, from `src/skills/topics/listening.md`) describes task enrichment, plan checks, waiting for answers, sequential work, and interruption recovery. An open question blocks that session until it is answered or withdrawn; listener mode does not skip it or treat its time as idle.

A resident agent follows `agboard skills resident` (`src/skills/topics/resident.md`) instead, and there are two kinds of it:

- **A session the board launched** works in push mode and never runs `wait`. The server watches the board and sends the session its work (see [Push mode](#push-mode)). The first instruction of a launched session (`prompt` in `src/server/resident/cli.rs`) tells it to run `agboard skills resident`, not to run `agboard wait`, to end its turn and wait for the board's messages, to ask only on the board, and to stop only when the board stops it. A unit test keeps those phrases in the prompt, and the skill tests keep the topic's.
- **A session a person told to stay on the board** keeps the pull model. It repeats the same `wait --until task` and handles answers, requests, and tasks as the listener procedure does, but it never ends on `idle_timeout`: a wait that times out or returns nothing to do is run again within a few seconds, because the registry keeps a closed event stream counted for only 30 seconds and a longer gap could let a second session launch. Claude Code runs the wait in the background, since the harness stops a long foreground command; Codex waits in the foreground.

A session the board launched runs headless with automatic approval, so it asks a person only on the board with `message ask --no-wait` and ends its turn; the answer is pushed back to it as an `answers` message.

`wait --until task` also tells the server which session is listening, so the board can count the sessions attached to it. Only external sessions do this: a session the board launched does not wait, and the server adds it to the count itself (see [Push mode](#push-mode)). Its event-stream request carries the session's key, tool, origin, and the project's ID in `X-Agboard-Session*` headers (see [Attached sessions](../reference/web-api.md#attached-sessions)), and the JSON it prints does not change. The command reads these from its own environment and sends nothing else from it:

- Origin: `AGBOARD_RESIDENT_ID` set (the board's launcher sets it) means `board`; otherwise `external`.
- Tool: `AGBOARD_SESSION_TOOL` (`claude-code` or `codex`; the board's launcher sets it) wins. Otherwise `CLAUDECODE` or `CLAUDE_CODE_SESSION_ID` means `claude-code`; `CODEX_THREAD_ID`, `CODEX_SANDBOX`, or `CODEX_SANDBOX_NETWORK_DISABLED` means `codex`; anything else is `unknown`. `CODEX_COMPANION_SESSION_ID` belongs to a Claude Code plugin, not to Codex, and is not used.
- Key: the first of `AGBOARD_RESIDENT_ID`, `CLAUDE_CODE_SESSION_ID`, and `CODEX_THREAD_ID` that is set, else the parent process ID. The key sent is a prefix (`resident`, `claude`, `codex`, or `ppid`) and the first 16 hex digits of the value's SHA-256, never the value. Where an agent starts a new shell for each command and sets none of these, the parent process ID differs from one command to the next, so such a session appears as several short ones; the board does not hide this.

The server counts a session while its stream is open and for a 30-second grace period after it closes, so a session that loops between waits stays one session. The registry is in server memory (`src/server/sessions/`), not saved. The Codex variables are the ones Codex documents for its commands; they were not checked against a running Codex when this was written.

### Launching resident agents

The board server can start a headless session of Claude Code or Codex in a project's bound folder, which then waits on the board like a session you started yourself. The launcher (`src/server/resident/`) is Agent Board's only dependency on those CLIs: nothing else names `claude` or `codex`, their flags, or their output. The routes are in [Launching sessions](../reference/web-api.md#launching-sessions). **A launched session runs unattended with automatic approval**; read [Sessions the board launches](./security.md#sessions-the-board-launches) first.

What the launcher does:

- **Check.** The CLI must be on the server's `PATH` (`agent_cli_missing` otherwise) and logged in (`agent_cli_logged_out`): `claude auth status` reports `loggedIn`, and `codex login status` exits 0. Each of these calls, and the model list, has a 20-second limit so a request never waits long; a login check that times out is `session_launch_failed`. `AGBOARD_CLAUDE_BIN` and `AGBOARD_CODEX_BIN` name an executable instead of searching `PATH`; the tests point them at fake scripts.
- **Models.** Claude Code has no command that lists models, so the launcher offers the fixed aliases `opus`, `sonnet`, `haiku`, and `fable`. Codex lists them with `codex debug models`, and only models whose `visibility` is `list` are offered. When that list cannot be read (the command is missing, fails, takes longer than 20 seconds, or prints something that is not the expected JSON), the list is empty with a `reason`, and a launch without a model uses the tool's own default. A model that is not offered is refused with `invalid_value`; so is a name that could be read as a flag.
- **Approval.** Claude Code runs with `--permission-mode auto --permission-prompts none`: a reviewer checks each action, and one that would ask is refused as a denied tool result, so nothing waits for a person. Codex runs as `codex app-server`; its thread is started with the workspace-write sandbox, `approvalPolicy` `on-request`, `approvalsReviewer` `auto_review` (automatic review, the counterpart of `--approve-for-me` of the old one-way launch), and the data area in `sandbox_workspace_write.writable_roots`, so the session's `agboard` writes are not blocked by the sandbox; `cwd` is the project folder. This is the only place these settings are named.
- **Launch.** One session in total, whichever tool or project. The launch is refused (`session_launch_refused`, with a reason that names the tool holding the slot) when this launcher already has a live child (which closes the gap before the session has started), when a restart is waiting, or when the registry counts a board-launched session of either tool. External sessions you started yourself are never limited. The child starts in the project's bound folder, and its output goes to `<data>/resident/<tool>.log`. The prompt tells it to use the skill and then end its turn; the board sends it work from then on.
- **Driver.** The launcher never speaks a CLI's wire format. It starts an `AgentDriver` (`src/server/resident/driver/mod.rs`) and reads its `DriverEvent`s on one thread per session; the supervisor, the health check, and the watcher only see those events. The trait has `start` (working folder, model, first prompt, writable folders, environment, log), `next_event`, `is_idle`, `send_user_message`, `answer_permission` (`Allow` or `Deny { reason }`), `interrupt`, `stop`, and `pid`. The events are `Started { session_id, tool_version }`, `Activity`, `PermissionRequest { id, kind, summary }`, `TurnEnded` (`Completed`, `Interrupted`, or `Failed`), `Unknown`, and `Exited { code, signal }`. **Only `Exited` ends a session.** A turn that ends does not, because Claude Code wakes itself when a background command finishes. `is_idle` tells whether the session is between turns, and `send_user_message` can be called at any time (Claude Code queues it while a turn runs; Codex steers the running turn). A permission request is decided by one function, `decide_permission`, which allows every request for now. `Launcher::with_factory` swaps the drivers, and the unit tests use `MockDriver` there, a scripted implementation of `AgentDriver` that records the calls it receives so tests can check them afterwards.
- **Claude Code.** `ClaudeDriver` runs `claude -p --input-format stream-json --output-format stream-json --verbose --permission-mode auto --permission-prompts none` (plus `--model`), so the permissions are the same as before. The first prompt is sent as a stream-json `user` message on standard input, and the input stays open for the life of the session, because closing it ends the session. Output is read line by line as JSON, reading only the fields it needs (a message it does not know is an `Unknown` event, and a line over 8 MiB is skipped), and the error stream is always drained into the log. The tool version from `system/init` is written to the log. In auto mode the CLI normally sends no permission request; one that does come (`can_use_tool`) is answered with a `control_response` (allow echoes the input as `updatedInput`, deny carries the reason), and a control request of an unknown kind gets an error response.
- **Codex.** `CodexDriver` (`codex.rs`) runs `codex app-server`, newline-delimited JSON-RPC on standard input and output with no `jsonrpc` field. It sends `initialize` (client name `agboard`) and `initialized`, then `thread/start` with `cwd`, `model` (only when one was chosen), `approvalPolicy: on-request`, `approvalsReviewer: auto_review`, `sandbox: workspace-write`, and `config.sandbox_workspace_write.writable_roots`. The first prompt is the first `turn/start`: it has the agent read the skill and end its turn without running `agboard wait`, and the board then sends each piece of work as a later turn (see [Push mode](#push-mode)). `Started` carries the thread ID and the version from the `userAgent` of the `initialize` result, which is also written to the log. `send_user_message` starts a turn when the session is idle and uses `turn/steer` while one runs; a steer the server refuses, or a message that arrives before the turn is known, waits and goes out as the next `turn/start` after `turn/completed`. `interrupt` is `turn/interrupt`, and `is_idle` follows `turn/started` and `turn/completed`; `turn/completed` with status `failed` is `TurnEnded(Failed)` with the error message. There is no request to end the server, so `stop` closes its input and then follows the same SIGTERM and SIGKILL steps as for Claude Code. The conversation is a state machine without a process (`codex_parse.rs`, `codex_inbound.rs`) that keeps the ids of our requests apart from the ids of the server's, and the `itemId` to item map, because the path of a file change appears only in its `item/started`. Only the fields it needs are read, and `hook/*`, `mcpServer/*`, `account/*`, token usage, and the like are ignored; a line over 8 MiB is skipped, and the error stream, which is tracing text, is drained into the log.
- **Approvals in Codex.** A request for approval that reaches the board (`item/commandExecution/requestApproval` or `item/fileChange/requestApproval`) becomes a `PermissionRequest` and is answered through `decide_permission`: `Allow` is `accept`, and `Deny` is `decline` without its reason, because the answer has no field for one. Any other request from the server is answered with the JSON-RPC error `-32601`, because an unanswered one stalls the turn. Automatic review normally answers first: in a live run of codex-cli 0.170.0 the server accepted `auto_review`, reported it back in the `thread/start` result, and sent no approval request to the board.
- **Environment.** The child gets the server's environment without `CLAUDECODE`, `CLAUDE_CODE_*`, `CODEX_*`, and `AGBOARD_RESIDENT_ID`, so the server's own agent session cannot make the child look like another tool. `CODEX_HOME`, `CODEX_API_KEY`, and `CLAUDE_CODE_OAUTH_TOKEN` are kept, because they configure or sign in the CLI. The launcher then sets `AGBOARD_RESIDENT_ID` (a random launch ID), `AGBOARD_SESSION_TOOL`, and `AGBOARD_SESSION_ORIGIN=board`, which is how the child's own `agboard` commands are told apart from an external session's: `message ask` records `AGBOARD_RESIDENT_ID` on each question it saves as `askedBy`, and a `wait` run with these variables reports origin `board`.
- **Stop.** The child is the leader of its own process group. Stop asks the driver to end it: the driver closes the child's standard input, gives it a short grace period (1.5 seconds), then sends SIGTERM to the group, and SIGKILL after 5 seconds. A command the child started that stays in the group after the child itself has left, such as one that ignores SIGTERM, gets the SIGKILL too. Stop then removes the session's entry from the registry at once, so a new launch is not refused for the 30-second grace period of a session that is gone. The same happens when the child exits by itself: a thread waits for every child, so none is left as a zombie. A stop, a launch, and a restart run one at a time, and a stop also cancels an auto-start or a restart that was prepared before it, so none of them brings the session back. When the server shuts down, it stops every launched child. A server that is killed outright cannot do this and leaves its children running.
- **Health and restarts.** A launch by a person makes the board keep that session running. When the child exits and nobody stopped it, the supervisor starts it again with the same project, tool, and model, after a wait of 2 seconds that doubles with each failure (up to 60 seconds). Five failures within 10 minutes stop the restarts: the health becomes `failed` with the reason, and it stays so until a person launches again. A session that stayed up for 10 minutes starts counting from zero. A failed attempt to start the process counts as a failure; a missing command, a logged-out tool, or a project that is gone is `failed` at once, because retrying cannot fix it. A stop by a person removes the plan, so it never leads to a restart and clears a waiting restart or a shown failure.
- **Unhealthy children.** A child that is alive but has never started is replaced. A child counts as attached when its driver reports its first `Started` or `TurnEnded` event, and the supervisor checks every second. A new child has 3 minutes to attach; if it never does, the supervisor ends it like a stop and records the reason (`never started`), and the exit counts as a failure like any other. After a child has attached once, only its exit ends it, because a turn on a task can take far longer than any limit. The health reports `waiting` (the session is attached and idle between turns) so a screen can show a running session as working. The registry plays no part in the health of a board-launched session.
- **Auto-start.** The choice to start a session with the server, one at most (the tool, the project, and the model), is saved in [`.internal/resident-autostart.json`](../reference/files.md#session-auto-start). When the server starts, a background thread launches it, so the server is listening before any CLI check runs. A start that fails does not stop the server: it shows as `failed` with the reason, and a failure of the process start is retried like a crash. Turning auto-start off does not stop a running session. The sessions response carries the [health](../reference/web-api.md#session-health) of the session.

### Push mode {#push-mode}

A session the board launched does not wait on the board. The server does: for each launched child, the launcher runs a pusher thread (`src/server/resident/push/`) that sends work through `AgentDriver::send_user_message`. A session a person opened in a terminal keeps the pull model and is not affected.

When the pusher looks. It wakes when the board changes (the server forwards its change feed to `Launcher::nudge`), when a turn ends (the event pump sees `TurnEnded`), and at least every `push_poll` (10 seconds) as a safety net. It does nothing unless the driver `is_idle()`, so it never sends while a turn runs; it waits for the turn to end and looks again. Claude Code receives the instruction as a stream-json `user` message and Codex as a plain `turn/start`, because an idle session has no turn to steer.

What it sends, in the order `wait --until task` uses, one instruction at a time:

1. Answers no agent has accepted, to questions that carry `askedBy`. `message ask` records `AGBOARD_RESIDENT_ID` there, so a question of a session the board launched is told apart from one an external session asked (its `askedBy` is absent). At most one launched session exists at a time, so a question with `askedBy` came from this run of the session or an earlier run, and either way this session is the one to tell. Answers to external sessions' questions stay with their own `wait` or `message wait`.
2. Open requests. The pusher reads the board right before it sends, so a request that an external session has already accepted (`message accept` succeeds only for the first caller) is not sent.
3. The next ready task, chosen like `wait --until task` does: an AI task in Todo or Doing that is Idle, not a draft, and not archived, and, for a Todo task, not held back by the waves of its epic. A task that someone is already working on is Running and is not sent. If an external session takes the same task at the same moment, the contention is the same as between two external sessions: the first to start it wins and the other re-reads and moves on.

The text is one sentence that tells the session to follow the "Work the board pushes" part of the resident skill and not to run `wait`, followed by the JSON that `wait --until task --json` would have returned for the same item (`kind`, `projectId`, `cursor`, and `answers`, `requests`, or `task`).

Failed turns. The pusher keeps a log of what it sent, per item (`answer:Q-3`, `request:Q-5`, `task:12`). An item still on the board after the turn that was given it is sent again only after a backoff that starts at `push_backoff_base` (30 seconds) and doubles up to `push_backoff_max` (5 minutes), and at most `push_max_attempts` (3) times. After that the item is skipped, and the health lists it in `pushStalled` with its kind, ID, number of attempts, and the message of the last failed turn. The other items keep going, so one item that fails does not block the board. An item that leaves the board (it is accepted, withdrawn, or no longer ready) leaves the log and the list. A stalled item that a person still wants handled needs a decision: stop and start the session, or finish the item by hand.

Stopped on an error. The pusher also remembers which tasks it handed in the turn that has not ended (`Push::handed`, set before the send so a turn that ends at once cannot miss it). When the event pump sees `TurnEnded(Failed)`, or the child exits in the middle of such a turn, `Launcher::hand_over` calls `FileStore::record_agent_stopped` (`src/file_store/ops/agent_stopped.rs`) for each of them. A task that is still an AI task Running in Doing gets one history entry and goes back to Idle in the same save; any other task (still Idle, moved, archived, a draft, Done) is left alone. The entry says that the resident agent stopped on an error, the first 200 characters of the failure message, and that another agent needs to take the task over. It follows the history language rule: Japanese when the task's text is Japanese, English otherwise. Setting the run state back is allowed by the state rules (an AI task may be Idle in Doing), and one save writes one entry, with no separate run-state entry. The handed tasks are kept per turn, oldest first, starting with an empty entry for the launch turn (the first prompt), so the end of the launch turn never takes the entry of a push that raced ahead of it. They are kept per push after that, and each turn end takes the oldest entry, so a push made while the pump has not yet handled the end of the previous turn (a reader can report idle first) never replaces it; one failure writes at most one entry per task, and a restarted child starts with an empty queue. Limit: run-state changes carry no actor, so the board cannot tell whether a task that is Running at that point was started by the resident session or by another agent that took it in the same moment. The pusher hands over only Idle tasks and the first to start wins, so the window is narrow, and the check stays at the task state (AI, Doing, Running). Nothing is written when the server is shutting down or when a person stopped the session (the supervisor's plan is gone by then). Because the task is Idle again, the retry rules above can hand it to the agent once more, and a new failure writes a new entry. See the user side in [Resident session](../../guide/delegate/resident-session.md#stopped-on-error).

Counts and health. The registry counts a session by its open `wait` streams, so a launched session does not appear there. `GET /api/projects/{id}/sessions` adds it to the list: `SessionList::with_session` merges the entry that `Launcher::board_session` builds (`origin: board`, the tool, and an `id` of `resident:` plus the launch ID) and recounts. It appears once the child reported its first event, as `connected` while it is idle between turns and as `grace` while it works, and external sessions are listed and counted as before. `waiting` in the health is true while the session is attached and idle. Health checks, restarts, and the crash-loop limit apply to the launched session only, and they read the driver's events (`Started`, `TurnEnded`, `Exited`), not the registry.

Tests. `src/server/resident/tests/push.rs` drives the launcher with `MockDriver` against a real board in a temporary folder: a request, an answer, and a task are sent to an idle session; nothing is sent during a turn or for an accepted request; only answers to the launched session's questions are sent; a failing item stops after three sends and is listed as stalled. `tests/resident_e2e.rs` runs both CLIs as fake scripts that never run `wait`, with an external `wait` counted beside the launched session.

## Automatic Done

The rule is defined in [Data model](./history-and-decisions.md#acceptance-conditions-and-automatic-done). Evaluation works like this:

- It re-reads the latest `TASK.md` and task fields under the FileStore project lock and applies one shared eligibility check.
- `serve` evaluates existing tasks at startup, before publishing the first snapshot. During operation it evaluates after FileStore saves and after atomic file updates seen by the watcher. It never re-triggers from its own notification, and re-evaluating the same task never duplicates history.
- A CLI edit that also changes the epic is evaluated after all changes apply. AI-facing CLI and FileStore entry points apply the Done guard.
- Tasks that wait for a person are skipped and re-evaluated after the answer. Done tasks never reopen automatically.
- Automatic Done needs a running server. The hook starts one, and a watcher-seen file change counts as use, so an automatic server does not stop while an agent keeps editing.
- Agents record verification in history, put concise results in the body, and only then set the last condition to `done: true`.
- Starting a new version of `serve` completes existing eligible tasks. Before adopting it for normal use, list those tasks and take a backup.

This restrains cooperative agents; it does not authenticate against direct file edits or a spoofed actor.

## The plugin

The Skill and the Hook are distributed as one plugin, `agent-board`, from a marketplace in this repository. Both agents install it with their own plugin commands, so agboard embeds no copy of the Hook and manifest files. The text of the Skill is the exception: the binary embeds it (see [The Skill from the binary](#the-skill-from-the-binary)), so the plugin's Skill is only an entry that asks `agboard` for it.

| Path | Contents |
| --- | --- |
| `.agents/plugins/marketplace.json` | The Codex marketplace catalog, named `agent-board`. |
| `.claude-plugin/marketplace.json` | The Claude Code marketplace catalog, named `agent-board`. |
| `plugins/agent-board/.codex-plugin/plugin.json`<br>`plugins/agent-board/.claude-plugin/plugin.json` | The plugin manifests. |
| `plugins/agent-board/skills/agent-board/` | The thin entry of the Skill: `SKILL.md` only. |
| `plugins/agent-board/skills/remote/` | The `remote` Skill: `SKILL.md` only. |
| `plugins/agent-board/skills/wait/` | The `wait` Skill: `SKILL.md` only. |
| `plugins/agent-board/hooks/codex.json`<br>`plugins/agent-board/hooks/claude.json` | The Hook of each agent. |

The plugin versions in both manifests equal the crate version, and the Hook commands carry no version: they are exactly `agboard hook --agent <agent>`. `tests/plugin_layout.rs` and `scripts/release/check-version.py` check this, so a release tag always holds a plugin of the same version as the binary.

## Hook skip and errors

The Hook resolves the project with `FileStore::resolve_binding`, which returns a `ResolvedBinding` (the project and the bound root). `project_for_folder` calls it, so ordinary commands keep their `folder_unbound` error.

| Input or state | Behavior |
| --- | --- |
| The `cwd` is a bound root, a subfolder, or inside a nearer nested binding | The nearest project only, as `AGBOARD_PROGRESS`. |
| The bindings are valid, the `cwd` is readable, and no binding matches | Nothing on stdout or stderr, exit code 0. The board is not read. |
| The nearest binding names a project that is gone | `bound_project_missing`. It never falls back to a parent. |
| The bindings file is malformed or unreadable | `AGBOARD_ERROR` with the cause. It is not treated as unbound. |
| The input is not valid JSON, has the wrong type, or is too large | `invalid_hook_input`, as before. |
| The `cwd` is missing, `null`, or empty | The process working folder is used. |
| The `cwd` is not a string, or is a relative path | `invalid_hook_input`. |
| The `cwd` does not exist or cannot be read | `hook_cwd_unavailable`. It is never turned into a skip. |
| An explicit `--project` | The named project wins. A name that is not found is `project_not_found`. |

The 256 KiB table, 10 second limit, event allowlist, and fixed command stay. The Hook never uses the network or writes settings. Starting the server is one side effect it has; the other is starting the [automatic plugin update](#automatic-plugin-update) in the background when the plugin differs. The only notice it adds is the one that update gives at session start. Older plugins still run the Hook with `--plugin-version <version>`; the option is accepted and ignored.

## The Skill from the binary

The `agent-board` Skill text is embedded in `agboard` at build time, so it always matches the binary that runs it. `agboard skills` prints the main text (`src/skills/agent-board.md`, without frontmatter). `agboard skills <topic>` prints one reference or template: `project`, `language`, `files`, `requests`, `work-loop`, `questions`, `waiting`, `file-format`, `listening`, `resident`, `planning`, `fixed-epic-bodies`, `drafts`, `phone`, `results`, `task-template`, `epic-template`, `bug-epic-template`, or `enhancement-epic-template` (`src/skills/topics/`). The main text holds only the rules an agent follows every time, and each of its sections points to the topic with the procedure, command usage, and examples. Claude Code inlines a `!` command's output only up to about 30,000 characters (a longer one is cut to a preview), so a unit test keeps the main text and every topic at 28,000 characters or fewer; move situational sections into topics when it grows. A name that is no topic prints the list of topics. The command reads and writes nothing, takes no lock, starts no server, uses no network, and always exits 0; this holds even when no data area can be resolved.

The plugin's `SKILL.md` keeps `name`, `description`, and `compatibility`, adds `allowed-tools: Bash(agboard *)`, and has one body line, `` !`agboard skills` ``. Claude Code replaces that line with the command's output when the Skill is invoked, and the `allowed-tools` rule lets the command and the agent's later `agboard` commands run without a prompt. The injection works only for a plain command: `$(...)` and compound commands are not replaced. Agents without command injection (Codex) read the sentence after it and run `agboard skills` themselves. The `remote` and `wait` Skills stay static in the plugin. The project's `.claude/skills/agent-board` is a symbolic link to the plugin's Skill folder, so this repository's own Claude Code sessions use the same entry and the `agboard` on `PATH`.

## Automatic plugin update

Both agents keep the plugin as a copy of the marketplace at an installed tag, so a new `agboard` leaves the old plugin in place. The build script (`build.rs`) hashes every file under `plugins/agent-board/` (a `.DS_Store` excluded) and embeds the file list and the hash (`src/plugin_hash.rs`, `src/setup/auto_update.rs`). The hash is FNV-1a over each relative path and file content. The plugin manifests hold the crate version, so every release changes the hash.

At SessionStart, after the progress table, the hook finds the installed plugin from the root variable the agent sets (`CLAUDE_PLUGIN_ROOT` for Claude Code, `PLUGIN_ROOT` for Codex with `CLAUDE_PLUGIN_ROOT` as a fallback), hashes the same relative files there (files the agent added are ignored; a missing file is a difference), and compares. A match, a missing or empty root variable, another hook event, or `AGBOARD_NO_PLUGIN_AUTO_UPDATE` set to anything but `0` does nothing. On a difference it starts `agboard update --agent <agent> --yes --background` as a detached process (`setsid`, no input or output), so the hook returns within its time limit, and adds an `AGBOARD_NOTICE`: the plugin is being updated to the version of `agboard` and applies from the next session. The notice is also the whole output when the folder is unbound.

The background run does what `agboard update` does for that agent, with these differences:

- **Lock.** It takes `<data>/plugin-update/<agent>.lock` (created exclusively; a lock older than 15 minutes is stale and replaced). Concurrent sessions see a live lock and do nothing, so the plugin is reinstalled once.
- **Record.** It writes `<data>/plugin-update/<agent>.json` (`hash`, `ok`, `at`, `version`) first with `ok: false` and again when it ends. For the same hash, a failed or unfinished attempt is not repeated for 6 hours, and the hook says instead that the automatic update did not complete and the user should run `agboard update`; a finished attempt that still leaves a different plugin (a build from a checkout) is not repeated for 24 hours and says nothing.
- **Trust.** Codex keys trust on the hook definition, and the definition is stable across releases. After the reinstall, the background run asks `plugin list --json` for the folder Codex installed the plugin into and trusts the Agent Board hooks, the way `agboard update --yes` does (`trust.rs`), only when the installed `hooks/codex.json` is byte-identical to the definition embedded in this binary. An unknown install folder, a definition that differs (for example the one-time move from hooks with `--plugin-version`), or a failure to trust trusts nothing and records the attempt as failed. The consent that `agboard setup` asked for covers trusting Agent Board's own hook; a changed or unknown definition is never trusted, and the user runs `agboard update` instead. The notice says this only when the definition changed.
- **Installed copies only.** The hook acts only when the plugin root lies inside a `plugins/cache` folder, which is where the agents keep marketplace installs; a checkout or `--plugin-dir` copy is left alone.
- **Tag check.** With the default source, before any agent command, it runs `git ls-remote --exit-code --tags <repo> refs/tags/v<version>` (15 second limit) and goes on only when that exits 0. Absent tag (exit 2, a development build ahead of the last release), network error, timeout, or no `git` all stop it and record a failed attempt, so it never removes a marketplace it cannot add again; the backoff decides when it tries again.
- **Silence.** It prints nothing and the hook never waits for it.

`AGBOARD_PLUGIN_MARKETPLACE` still replaces the source, as for `agboard update`; tests use it with the fake agents of `tests/support/fake_agents.rs`. For what users see, see [Update the plugin](../../guide/delegate/agents.md#update-the-plugin).

## Setup and update

`agboard setup` and `agboard update` share `src/setup/`, and `src/cli/commands/setup.rs` handles both. They branch before normal store handling, need no project, and resolve the data area once through the shared path resolution. For what users see, see [Set up your agents](../../guide/delegate/agents.md#set-up-your-agents) and [Setup and update](../../guide/reference/cli.md#setup-and-update).

A run has two phases:

1. **Prepare (read-only).** `prepare.rs` finds each agent's command on `PATH`, reads the installed plugin with `plugin list --json` (its version and, when the listing names the folder it was installed into, whether its files hash like the shipped plugin), and, for `setup`, reads and plans the settings files. An agent whose command is missing is skipped with the reason. `update` skips an agent that has no plugin. A settings file that cannot be used stops the whole run before anything is written. A dry run stops after this phase, so it uses the same checks. `setup` plans an install when the plugin is missing or its files differ from the shipped ones (its version, when the folder is unknown), and skips it otherwise; `update` always reinstalls.
2. **Execute.** After the user agrees, `execute.rs` creates the shared folder and writes the settings files, all or none. It then runs each agent's plugin commands and, for Codex, trusts the hooks. A failure in this step stops only that agent; the files already written stay, because they are correct on their own and the command can be run again.

The pieces:

- **Agent commands.** `agent_cli.rs` finds `codex` and `claude` on `PATH` without a shell, runs them with no input and a time limit, and captures their output. Tests put fake commands first on `PATH` (`tests/support/fake_agents.rs`), so no test reaches a real agent or the network.
- **Plugin install.** `plugin.rs` adds the marketplace at the tag `v<version>` of `https://github.com/FooQoo/agent-board.git`, then runs `codex plugin add agent-board@agent-board`, or `claude plugin install` and `claude plugin update`. When the marketplace was already added from another source (Codex reports that it is added from a different source; Claude Code reports the failure code `declared`), it removes the marketplace and adds it again. This is how both agents move a marketplace to a new tag. `AGBOARD_PLUGIN_MARKETPLACE` replaces the source with another location, such as a local checkout, for development.
- **Settings files.** `plan.rs`, `codex.rs`, and `claude.rs` compute the new bytes of each file. Codex TOML is edited with `toml_edit`, preserving comments, other keys, and arrays; Claude Code JSON keeps unknown keys. Codex gets the data folder in `sandbox_workspace_write.writable_roots` and the rules file `$CODEX_HOME/rules/agboard.rules`; Claude Code gets it in `permissions.additionalDirectories`. `update` changes no settings file.
- **Writing.** `apply.rs` and `apply/files.rs` back up each existing file to `<file>.agboard-backup…` in the same folder, replace it through a temporary file and a rename, and undo what this run wrote when a later write fails. A file that changed after planning is never overwritten. Symbolic links are resolved and the real file is edited.
- **Hook trust.** `trust.rs` starts `codex app-server`, lists the hooks with `hooks/list`, and stores the current hash of each Agent Board hook under `hooks.state` with `config/value/write`. Only the plugin's own hooks are touched. Codex ties trust to the plugin's content, so every install or update trusts the hooks again.
- **Report.** `report.rs` gives each agent `updated`, `unchanged`, `planned`, `skipped`, or `failed`, as text or JSON. The exit code is 1 when an agent failed, or when `setup` could set up no agent.

Setup never switches permission modes or managed settings. What it may and may not grant is part of the [Security model](./security.md#agent-access-setup).
