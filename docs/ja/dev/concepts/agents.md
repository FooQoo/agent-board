# エージェント連携

エージェント連携は、作業手順を定める**スキル**、進行表を渡す**Hook**、変更や回答を待つ`wait`で構成されます。このページでは、それぞれの役割と、`agboard setup`によるアクセス設定を説明します。利用者向けの作業の流れは[エージェントとの連携](../../guide/automation/agents.md)、エージェントが受け取るJSONは[Hook・進行表・waitの出力](../reference/agent-output.md)にあります。

## 各部分の関係

| 部分 | 場所 | 役割 |
| --- | --- | --- |
| スキル`agent-board` | `.agents/skills/agent-board/SKILL.md` | 判断。作業の選び方、進捗の報告、判断依頼の出し方、下書きとDoneのタスクの扱い。 |
| Hook | `agboard hook`（`src/agent/hook.rs`） | 取得と整形。ツールの呼び出しの後に、現在の進行表をエージェントのコンテキストに添える。 |
| 進行表 | `src/progress.rs` | 進められるタスクの一覧。`agboard progress`とHookが共有する。 |
| `wait` | `src/agent/wait.rs` | プロジェクトが変わるか、判断依頼に回答があるまで待つ。 |

スキルの名前は`agent-board`、実行ファイルは`agboard`です。典型的な流れは次のとおりです。Hookが進行表を見せる → エージェントは必要な`PLAN.md`と`TASK.md`だけを読む → タスクをDoingとRunningにする → `history add`で進捗を記録する → ユーザーの判断が必要になったら`"wait": {}`付きで判断依頼を出す → 条件を満たしていき、自動Doneがタスクを完了させる。

エージェントは、開始・意味のある進捗・判断・検証・中断・再開のときに、項目ごとの承認なしで進捗を追加し、操作時に自動で記録された履歴は重複して追加しません。本文には計画・結果・証跡への参照を書き、全文のログは証跡ファイルに置きます。

## 進行表とHook

進行表は、Pending以外のTodoとDoingのタスクを、エピックごとに`priority`の順で並べた一覧です。各タスクのID・タイトル・担当・状態・受入条件の件数と、`PLAN.md`と`TASK.md`のパスを含み、本文や履歴は含みません。優先するタスクがPendingでも、後続のタスクは進められます。回答を受け取り、まだ完了していないタスクは一覧に戻ります。

Hookは、入力の`cwd`（なければプロセスのcwd）に最も近い紐付け済みの祖先からプロジェクトを識別します。セッションIDは使わず、紐付けがないときに全プロジェクトを選ぶこともありません。一覧は`hookSpecificOutput.additionalContext`に`AGBOARD_PROGRESS`のJSONとして返し、失敗したときは`folder_unbound`などの`AGBOARD_ERROR`を返します。

- **Claude Code。** `integrations/claude-code/`のテンプレートが、プロジェクト名を固定せずに`agboard hook`をPostToolUseに、失敗の後はPostToolUseFailureに登録します。汎用スキルのfrontmatterのHookは使いません。スキルは最初の読み込み時にスナップショットを読み、コンテキスト圧縮後（SessionStartの`compact`）か次のツールの完了時に一覧を取り直します。
- **Codex。** `integrations/codex/`のテンプレートが`agboard hook --agent codex`をPostToolUseに登録し、最初の利用時とコンテキスト圧縮後にも取得します。既存の設定に自動で書き込むことはなく、利用者がテンプレートを確認して信頼します。
- **上限。** 入力はUTF-8で64 KiB、一覧は256 KiB、一回の実行は10秒が上限です。Codexの`additionalContextLimit`は0にし、Hookが自分の上限を守ります。超えたら`context_too_large`を報告し、切り詰めて成功として報告することはありません。一覧を作れない、または入力の全体が届かなかったときは、Hookがそれを伝え、元のツールの結果を保ちます。
- **安全性。** コマンドは固定で、タスクのテキストや`tool_input`から何も組み立てません。Hookがエージェントのツールを呼ぶことも、自分自身を起動することも、ファイルを変えることもありません。パスはローカルのCLIとHookの出力にだけ現れ、リモート向けのJSONには出しません。

エージェントは、一覧を読めるまでボードに依存する変更をせず、コンテキスト圧縮後には一覧を新しく読みます。

## 変更を待つ

`agboard wait --after <cursor>`は、プロジェクトが変わるまで待ちます。

1. 同じデータ領域の`serve.json`から`pid`と`port`を読み、`GET /api/events`に接続します。
2. プロジェクト名をcursorと照合して、ProjectIdを固定します。別のプロジェクトや旧形式のcursorは`cursor_invalid`です。
3. `ready`の後に、プロジェクトの現在のversionとcursorを比べます。違えばすぐに返します。これにより、初回取得から購読開始までに起きた変更も検知できます。
4. 同じなら`changed`を待ちます。読み直してもversionが同じ（ほかのプロジェクトが変わった）なら、待ち続けます。

- `changed`・`ready`・接続維持のコメントは区別します。名前変更では同じプロジェクトのスナップショットを返し、削除では`project_not_found`を返して、作り直したプロジェクトへは移りません。
- 接続の上限は3秒で、待機そのものは既定で無期限です。任意の`--timeout`を付けると、最後にversionをもう一度確かめ、変わっていなければ`wait_timeout`を返します。切断は`board_unavailable`です。自動で短い再試行を繰り返すことも、定期的にポーリングすることもありません。
- 切断・時間切れ・Ctrl+Cでタスクや履歴が変わることはなく、「変更なし」として扱うことも、終了したエージェントを起動し直すこともありません。
- CLIの通知はベストエフォートなので、通知を取りこぼした場合は、次の接続、実際の`changed`、または時間切れ時の最終読み込みで変更を検知します。

**`"wait": {}`付きの判断依頼**は、一つのコマンドで依頼と待機を行います。質問は、回答されるか、列移動で取り下げられる（`request_changed`）までPendingのままで、待機を終えたり中断したりしても失効しません。待っていたコマンドは、解決した回答を`answer`で返します。ローカルの待機クライアントはHTTPのリダイレクトに従わず、127.0.0.1の同じ`serve`だけに接続します。

## 自動Done

規則は[データモデル](./history-and-decisions.md#受入条件と自動done)で定めています。評価は次のように行います。

- FileStoreのプロジェクトロックの中で、最新の`TASK.md`とタスクの項目を読み直し、共通の判定を一つ適用します。
- `serve`は起動時、最初のスナップショットを公開する前に既存のタスクを評価します。稼働中は、FileStoreの保存の後と、監視が捉えた原子的なファイル更新の後に評価します。自分の通知で再び評価が始まることはなく、同じタスクを評価し直しても履歴は重複しません。
- エピックも変えるCLIの編集は、すべての変更を適用した後に評価します。AI向けのCLIとFileStoreの入口は、Doneの制限を適用します。
- Pendingのタスクは飛ばし、回答の後に評価し直します。Doneのタスクが自動で再開することはありません。
- エージェントは、検証を履歴に記録し、結果と証跡への参照を本文に書いてから、最後の条件を`done: true`にします。
- 新しい版の`serve`を起動すると、条件を満たした既存のタスクが完了します。通常の利用に導入する前に、対象のタスクを一覧にしてバックアップを取ってください。

この制限は、ルールに従うエージェントの誤操作を防ぐためのものです。ファイルの直接編集やactorの偽装を防ぐ認証機能ではありません。

## setupでアクセスを準備する

`agboard setup`は、エージェントが共有ファイルを編集できるよう、Agent Boardのデータ領域をエージェントの許可されたフォルダに加えます。利用者が一度だけ実行する手順で、プロジェクトの作成やHookの登録はしません。

内部処理は次のように分かれています。

- 通常のストアの処理より前に分岐し、共通のパス解決でデータ領域を一度だけ解決します。
- 環境とパスの解決、変更計画、CodexのTOMLの編集（`toml_edit`でコメント・ほかのキー・配列を保つ）、Claude CodeのJSONの編集（未知のキーを保つ）、退避と適用を別の段階に分けます。変更計画は各ファイルの元の内容と更新後の内容を持ち、dry runも同じ検証を使います。
- 許可モードや管理設定は切り替えません。現在の方式で変更できるかを確かめ、書き込む前にすべての対象を検証し、その間に元のファイルが変わっていないことを確かめます。ファイルを書いたことと、エージェントがそれを読み込んだことは分けて報告します。

失敗したとき:

- 不正なJSONやTOML、対応しない権限の方式、並行する変更があれば、何も書く前に止まり、対象・理由・次の手順を報告します。
- 変更するファイルは、同じフォルダの一意なファイルに退避してから、一時ファイルで置き換えます。変わらないファイルは退避も書き込みもしません。
- 実行が途中で失敗したら、その実行が書いたものだけを、外部の変更を上書きせずに戻します。戻せなければ完了として報告せず、何が変わり、退避先がどこかを示します。
- シンボリックリンクは解決して実体のファイルを編集します。解決できないパスは、推測せずに止まります。
- dry runはフォルダ・設定ファイル・退避を作りません。setupは古いデータや、稼働中のサーバーの通知先を変えません。

付与するアクセス権の範囲は、[セキュリティモデル](./security.md#エージェントのアクセス設定)の一部です。
