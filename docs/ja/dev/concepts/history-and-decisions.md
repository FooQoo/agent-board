# 履歴と判断依頼

操作や進捗を残す履歴、人の判断を待つPendingと回答、受入条件に基づく自動完了の仕組みを説明します。

## 判断依頼と回答

エージェントは人の判断が必要になると、質問と選択肢を付けてタスクをPendingにします。

- CLIは、質問（1〜5,000文字、Markdown）と2〜10件の選択肢を`--request-json`で受け取ります。各選択肢は依頼内で一意のID（`[A-Za-z0-9_-]`の1〜64文字）と1〜200文字のラベルを持ちます。選択肢が1件以下や11件以上の依頼は拒否するため、どの判断依頼にも選べる選択肢があります。自由記述での回答は引き続きできます。
- 新しい`pendingRequestId`を作り、`pendingRequest`に`{question, choices}`を保存します。履歴には、質問と選択肢を別々のブロックにした項目を追加します。
- すでにPendingのタスクに同じ依頼をしても、質問は差し替わりません。設定済みの状態は変更にならないためです。質問を取り下げるのは、列の移動（完了への移動を含む）とアーカイブだけです。取り下げたあとに、新しい質問を出します。
- 回答は現在の依頼IDを指定しなければならず、違えば`request_changed`で失敗します。`choiceId`、`text`（前後の空白を除いて1〜2,000文字）のどちらか、または両方を受け付け、どちらもないものは拒否します。未知の選択肢は`request_choice_unknown`です。回答は選択時のラベルとともに`requestAnswers`に保存し、依頼を解除し、タスクを同じレーンのIdleに戻し、質問・選んだラベル・メモを別々のブロックにした履歴を追加します。Runningへ戻すのは別の変更です。
- 質問と回答の文は前後の空白を除き、CRLFと単独のCRをLFに正規化します。

ワークフロー情報を履歴の文章から推測することはありません。現在の質問は`pendingRequest`から、回答は`requestAnswers`から読むので、履歴を編集してもこれらは変わりません。

## 履歴

履歴には、作業の進捗とタスクの操作を時系列で記録します。各項目は、保存・API・CLIのどこでも、次の二つのフィールドだけを持ちます。

- `at`: 厳密に`YYYY-MM-DDTHH:MM:SSZ`の形のUTCの日時。
- `reason`: 1〜10,000文字で、空白だけではない内容。

ID・種別・actor・遷移・依頼IDなどの追加の項目は拒否します。

- 作成・列移動・稼働状態の変更・判断依頼・回答・下書きの切り替え・エピックの変更・アーカイブ・復元・人による条件の付け外し・自動Doneは、履歴を自動で追加します。移動やPending以外の状態の変更で理由を省くと、操作と現在の状態から生成します。
- エージェントは`agboard --project NAME history add ID [--reason TEXT | --reason-file PATH]`で作業の進捗を追加します。日時はAgent Boardが自動で付け、下書き・アーカイブ済み・DoneのタスクへのAIの追加は拒否します。空白の理由は、現在のレーンと稼働状態から生成します。
- エージェントは、開始・意味のある進捗・判断・検証・中断・再開のときに、記録ごとの承認を求めずに簡潔な項目を記録し、操作時に自動で記録された履歴は重複して追加しません。
- 画面は日時と内容だけを新しい順に表示し、理由は本文と同じMarkdownで描きます。CLIの`show`とスナップショットは全履歴を返します。

ブラウザ操作で自動生成する履歴は、そのリクエストで送られた画面の言語設定（`en`または`ja`）を使います。有効な設定がない操作、CLI操作、自動Doneでは、最新のタスク本文に日本語の文字があれば日本語、それ以外は英語を使います。本文が空か標準テンプレートのままならタイトルを使います。frontmatterと過去の履歴は判定に含めません。明示された空でない理由はそのまま保存し、既存の履歴を翻訳し直すことはありません。

AIが書く履歴は本文と同じ言語にし、理由を明示します。手順は[エージェント連携](./agents.md)で定めています。

## 受入条件と自動Done

管理対象の受入条件を持つのは`TASK.md`だけで、履歴と一緒にfrontmatterに置きます。

```markdown
---
acceptance:
  - id: AC-1
    text: List tasks as JSON.
    done: false
history: []
---

(Task plan, verification results, references to artifacts)
```

- `acceptance`はリストで、省略・`null`・空はどれも0件です。各項目はちょうど`id`（先頭に0を付けない`AC-<正の整数>`、ファイル内で一意）、`text`（前後の空白を除いて1〜2,000文字）、`done`（真偽値）を持ちます。番号は振り直しません。
- ほかのトップレベルのキーは保存時に保ちます（YAMLの書式は正規化されることがあります）。frontmatterのないファイルや、見出しと`- [ ] AC-n.`の行による旧形式は条件0件として読み、移行しません。
- 本文には計画・簡潔な検証結果・成果物への参照を書き、時系列の進捗は`history`だけに書きます。

**自動Done**: AI担当・下書きでない・未アーカイブのTodoかDoingのタスクで、有効な条件が1件以上あり、すべて`done: true`になると、タスクは自動でDoneに移ります。履歴に一件記録し、`taskStatusChangedAt`を更新します。Pendingのタスクは回答されるまで待ち、回答後に評価し直します。条件がない・不正なタスク、人間担当、下書きは対象外です。`serve`は起動時にも既存のタスクを評価します。

**人によるチェック**: 人は、ボードかモバイルモニターから、条件を1件ずつ付け外しします（`PUT .../tasks/{id}/acceptance/{condition}`に`{"done": true|false}`を送ります。[Web API](../reference/web-api.md)を参照）。要求に版は含めません。FileStoreは、プロジェクトのロックの中で最新の`TASK.md`を読み、その条件だけを変え、履歴を一件足して保存します。そのため、読み込んだあとに加えられた変更より人の選択が優先され、本文・ほかの条件・エージェントのほかの編集は残ります。アーカイブ済みのタスクは拒否し（`task_archived`）、存在しない条件は`invalid_argument`です。そのあとwatcherが、ほかの変更と同じく自動Doneを評価します。そのため、対象のAIタスクで最後の条件にチェックが入るとDoneに移り、Doneのタスクで条件を外してもDoneのままです。

DoneのタスクはAIの変更（編集・状態・エピック・履歴・画像）を拒否し、自動で再開することはありません。人は編集も再開もできます。未達成の条件が残る、またはfrontmatterが不正なとき、AIの列移動によるDoneへの移動は`acceptance_unmet`で拒否します。条件0件のタスクと人の移動は止めません。評価の仕組みは[エージェント連携](./agents.md#自動done)にあります。
