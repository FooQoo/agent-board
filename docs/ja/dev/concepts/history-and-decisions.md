# 履歴と判断依頼

操作や進捗を残す履歴、人に尋ねる質問と回答、完了条件に基づく自動完了の仕組みを説明します。

## メッセージ

メッセージはタスクではなくプロジェクトに属します。メッセージには、AIから人への質問と、人からAIへの依頼があります。タスクは待っている質問を参照します。

- メッセージは1件1ファイルで、`qa/Q-<n>/QA.md`に保存します。YAMLのfrontmatterとMarkdownの本文で構成します。依頼に添付した画像は`qa/Q-<n>/attachments/`に置きます。質問と依頼は`project.json`の`nextQuestionId`の1本の連番を共有し、番号は増えるだけです。
- 質問は`from`、`to`、任意の`tasks`（質問の対象タスク）、任意で2〜10件の`choices`、任意の`recommended`、`reply`、`withdrawnAt`、`createdAt`を持ちます。本文が質問で、1〜5,000文字です。各選択肢は質問内で一意のID（`[A-Za-z0-9_-]`の1〜64文字）と1〜200文字のラベルを持ちます。`recommended`は選択肢のどれかを指します。
- 依頼は`from`、`to`、`acceptedAt`、`withdrawnAt`、`createdAt`を持ちます。本文が依頼で、1〜20,000文字です。
- `agboard message ask`は質問1件につき1ファイルを書き、1回に20件まで出せます。`--task <id>`または質問の`tasks`を指定すると、そのタスクのfrontmatterの`questions`に質問IDを足し、質問と選択肢を別々のブロックにした履歴を追加します。Runningのタスクは同じ保存でIdleに戻します。指定したタスクが存在しない、アーカイブ済み、下書き、またはAIの操作でDoneのときは、何も書きません。
- 回答は`{choice, text, via, at}`に任意の`acceptedAt`を加えた形です。選択肢のある質問には`choice`か`text`（または両方）が必要で、メモだけの回答は`choice`が`null`の回答になります。選択肢のない質問には`text`が必要です。`text`は前後の空白を除いて1〜2,000文字です。未知の選択肢は`choice_unknown`です。回答には選択肢のID、`via`（ボードとリモートアクセスからは`ui`、チャットで受けた回答をエージェントが記録したときは`chat`、端末からは`cli`）、時刻を保存します。質問を参照しているアーカイブされていないタスクには、質問・選んだラベル・メモを別々のブロックにした履歴を追加します。Doneのタスクにも追加します。
- 回答を書けるのは人だけで、1回だけです。回答済みの質問に答えると`question_answered`で失敗します。まとめて送った回答は、全部書くか何も書かないかのどちらかです。
- 依頼は、エージェントが`agboard message accept`で受け付けます。`acceptedAt`を記録します。受け付けは1回だけで、2回目は`request_accepted`で失敗します。
- エージェントは、回答済みの質問も`agboard message accept`で受け付けます。`reply.acceptedAt`を記録し、回答を受け取った状態にします。回答のない質問を受け付けると`question_open`、2回目は`answer_accepted`で失敗します。`agboard message ask`と`agboard message wait`は、質問が回答または取り下げで終わって待機が終わったとき、返した回答を受け付けます。エージェントがチャットから書いた回答（`via: chat`）は、書かれた時点で受け付け済みです。受け付けられるまでの回答は、進行表・Hook・`wait --until task`の`answers`に載ります。
- 取り下げたメッセージには何も書きません。回答は`question_withdrawn`、受け付けは`request_withdrawn`で失敗します。質問を取り下げられるのはエージェントだけ（人は`ai_only`）、依頼を取り下げられるのは人だけ（エージェントは`human_only`）です。すでに回答または受け付けのあるメッセージは取り下げられません（`message_closed`）。すでに付いた回答は残ります。レーンの移動、アーカイブ、削除でメッセージが取り下げられることはありません。
- `message link`と`message unlink`は、タスクの`questions`に参照を足したり外したりし、質問側の`tasks`も合わせて更新します。`TASK.md`の編集と同じ制限がかかり、履歴を追加します。
- メッセージの文は前後の空白を除き、CRLFと単独のCRをLFに正規化します。

メッセージの状態は3つです。`withdrawnAt`があれば`withdrawn`、質問に回答がある、または依頼が受け付け済みなら`closed`（回答の受け付けは状態を変えません）、それ以外は`open`です。状態は保存せず、ファイルを読むときに導きます。APIとCLIでは、質問は`open`・`answered`・`withdrawn`、依頼は`open`・`accepted`・`withdrawn`と呼びます。絞り込みには`open`・`closed`・`withdrawn`・`all`を使えます。

### 人の判断待ち

AIタスクが人の判断待ちになるのは、回答のない質問を参照しているとき、読めないメッセージのファイルを参照しているとき、またはfrontmatterの`questions`を読めないときです。取り下げた質問では待ちになりません。すべてのメッセージのファイルが読める状態で、存在しないメッセージを指す参照も待ちにはならず、`problems`に載せます。

`task.json`に保存するのは`idle`か`running`だけです。TodoかDoingのAIタスクが判断待ちのときは、Summary、snapshot、`show`、進捗表、hookのどれも`agentStatus`を`pending`として返し、`openQuestionIds`と、IDが最も小さい未回答の質問から`pendingReason`と`pendingChoices`を返します。判断待ちの間、AIによる`state <id> running`とDoneへの移動は`questions_unanswered`で失敗します。`idle`への変更と人の移動は通します。Done、アーカイブ済み、人のタスクは保存した状態を表示し、参照は記録として残ります。

ワークフロー情報を履歴の文章から推測することはありません。メッセージは`QA.md`から、参照はfrontmatterの`questions`から読むので、履歴を編集してもこれらは変わりません。

## 履歴

履歴には、作業の進捗とタスクの操作を時系列で記録します。各項目は、保存・API・CLIのどこでも、次の二つのフィールドだけを持ちます。

- `at`: 厳密に`YYYY-MM-DDTHH:MM:SSZ`の形のUTCの日時。
- `reason`: 1〜10,000文字で、空白だけではない内容。

ID・種別・actor・遷移・依頼IDなどの追加の項目は拒否します。

- 作成・列移動・稼働状態の変更・質問・回答・取り下げ・参照の変更・下書きの切り替え・エピックの変更・アーカイブ・復元・人による条件の付け外し・自動Doneは、履歴を自動で追加します。移動や状態の変更で理由を省くと、操作と現在の状態から生成します。
- エージェントは`agboard --project NAME history add ID [--reason TEXT | --reason-file PATH]`で作業の進捗を追加します。日時はAgent Boardが自動で付け、下書き・アーカイブ済み・DoneのタスクへのAIの追加は拒否します。空白の理由は、現在のレーンと稼働状態から生成します。
- エージェントは、開始・意味のある進捗・判断・検証・中断・再開のときに、記録ごとの承認を求めずに簡潔な項目を記録し、操作時に自動で記録された履歴は重複して追加しません。
- 画面は日時と内容だけを新しい順に表示し、理由は本文と同じMarkdownで描きます。CLIの`show`とスナップショットは全履歴を返します。

ブラウザ操作で自動生成する履歴は、そのリクエストで送られた画面の言語設定（`en`または`ja`）を使います。有効な設定がない操作、CLI操作、自動Doneでは、最新のタスク本文に日本語の文字があれば日本語、それ以外は英語を使います。本文が空か標準テンプレートのままならタイトルを使います。frontmatterと過去の履歴は判定に含めません。明示された空でない理由はそのまま保存し、既存の履歴を翻訳し直すことはありません。

AIが書く履歴は本文と同じ言語にし、理由を明示します。手順は[エージェント連携](./agents.md)で定めています。

## 完了条件と自動Done

管理対象の完了条件を持つのは`TASK.md`だけで、履歴と一緒にfrontmatterに置きます。

```markdown
---
acceptance:
  - id: AC-1
    text: List tasks as JSON.
    done: false
history: []
---

(Task plan, verification results, references to artifacts)
```

- `acceptance`はリストで、省略・`null`・空はどれも0件です。各項目はちょうど`id`（先頭に0を付けない`AC-<正の整数>`、ファイル内で一意）、`text`（前後の空白を除いて1〜2,000文字）、`done`（真偽値）を持ちます。番号は振り直しません。
- ほかのトップレベルのキーは保存時に保ちます（YAMLの書式は正規化されることがあります）。frontmatterのないファイルや、見出しと`- [ ] AC-n.`の行による旧形式は条件0件として読み、移行しません。
- 本文には計画・簡潔な検証結果・成果物への参照を書き、時系列の進捗は`history`だけに書きます。

**自動Done**: AI担当・下書きでない・未アーカイブのTodoかDoingのタスクで、有効な条件が1件以上あり、すべて`done: true`になると、タスクは自動でDoneに移ります。履歴に一件記録し、`taskStatusChangedAt`を更新します。人の判断待ちのタスクは飛ばし、回答が届いたら評価し直します。条件がない・不正なタスク、人間担当、下書きは対象外です。`serve`は起動時にも既存のタスクを評価します。

**人によるチェック**: 人は、ボードかリモートアクセスから、条件を1件ずつ付け外しします（`PUT .../tasks/{id}/acceptance/{condition}`に`{"done": true|false}`を送ります。[Web API](../reference/web-api.md)を参照）。要求に版は含めません。FileStoreは、プロジェクトのロックの中で最新の`TASK.md`を読み、その条件だけを変え、履歴を一件足して保存します。そのため、読み込んだあとに加えられた変更より人の選択が優先され、本文・ほかの条件・エージェントのほかの編集は残ります。アーカイブ済みのタスクは拒否し（`task_archived`）、存在しない条件は`invalid_argument`です。そのあとwatcherが、ほかの変更と同じく自動Doneを評価します。そのため、対象のAIタスクで最後の条件にチェックが入るとDoneに移り、Doneのタスクで条件を外してもDoneのままです。

DoneのタスクはAIの変更（編集・状態・エピック・履歴・画像）を拒否し、自動で再開することはありません。人は編集も再開もできます。未達成の条件が残る、またはfrontmatterが不正なとき、AIの列移動によるDoneへの移動は`acceptance_unmet`で、人の判断待ちのあいだは`questions_unanswered`で拒否します。条件0件のタスクと人の移動は止めません。評価の仕組みは[エージェント連携](./agents.md#自動done)にあります。
