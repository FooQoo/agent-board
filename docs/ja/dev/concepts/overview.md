# Agent Boardの仕組み

Agent Boardの役割、構成、データの保存先、エージェントの操作がブラウザへ反映されるまでの流れを説明します。開発を始める際は、まずこのページで全体像を確認してください。各機能の詳細は、関連する解説ページで扱います。

## 二層のハーネス

Claude CodeやCodexのようなAIエージェントは、自分のハーネスの中で動きます。呼び出せるツール、保持するコンテキスト、動かし続けるループです。このハーネスが決めるのは、一つのセッションの中でエージェントがどう働くかです。何が仕事か、いつ終わりか、いつ人に尋ねるかは決めません。また、セッションを超えては残りません。

Agent Boardは、その上に載る**仕事のハーネス**です。計画、終わりを決める完了条件、人が答えるまでエージェントを止める質問、次のセッションが続きから始められる履歴を持ちます。これらはどのエージェントの外にもあるファイルに保存されるので、別のエージェントや新しいセッションが、前の続きから仕事を引き継げます。

```mermaid
flowchart LR
    Agent["エージェントのハーネス<br/>ツール・コンテキスト・ループ"] --> Work["Agent Board<br/>計画・完了条件・<br/>質問・履歴"]
    Work --> Monitors["モニター<br/>ボード・スマホ・チャット・CLI"]
    Person["人"] --> Monitors
```

ボード、スマホ、チャット、`agboard`コマンドは、別々の機能ではなく、同じ仕事のモデルを見て、答えて、介入するモニターです。どれも同じファイルを同じ操作で読み書きするので、どのモニターを使っても規則は同じように働きます。その規則と、コードのどこで守られているか、まだエージェントに頼っているのはどこかは、[仕事のモデルと実装](./work-model.md)にまとめています。利用者から見たモデルは[仕事のモデル](../../guide/work-model.md)を参照してください。

このページの残りでは、モデルを支える実装を説明します。

## 全体像

Agent Boardは、一つのRust製実行ファイル`agboard`です。同じバイナリが、エージェントや人が実行するCLIと、ブラウザにボードを表示するWebサーバー（`agboard serve`）の両方を担います。

データベースは使わず、すべてのプロジェクトを共有領域内のファイルに保存します。保存先は、ホームディレクトリの`.agent-board/shared/`、または`AGBOARD_HOME`配下です。人とエージェントが書くもの（タスクの本文、完了条件、履歴、エピックの詳細）はMarkdownに、操作上の状態（レーン、稼働状態、プロジェクトの質問と回答）はJSONに保存します。ファイルが正本なので、エージェントは`TASK.md`と`EPIC.md`を直接編集してもよく、サーバーが変更を検知して表示へ反映します。

### データの読み書き

CLIとブラウザは、同じローカルファイルを読み書きします。タスクの状態は`task.json`、本文・完了条件・履歴は`TASK.md`、エピックの詳細は`EPIC.md`に保存されます。

```mermaid
flowchart LR
    CLI["CLI"] --> Files[("共有ファイル")]
    Files <--> Serve["agboard serve"]
    Serve <--> Browser["ブラウザ"]
```

エージェントは`agboard add`・`mv`・`state`などでタスクを操作し、ユーザーはブラウザから操作します。`rm`や`init`による削除・初期化はユーザーがCLIで行います。`TASK.md`と`EPIC.md`は直接編集することもでき、サーバーが変更を検知します。CLIの保存には、ロックと一時ファイルのrenameを使います。

### 変更の通知

CLIは`POST /api/notify`で保存を通知し、ファイルの直接編集はOSの変更イベントで検知されます。サーバーは変更されたプロジェクトを読み直し、画面に表示する内容が変わっていれば`SSE: changed`で変更されたリソースを知らせます。ブラウザは、Summaryを読み直し、開いている詳細のうち変わったものだけを読み直します。

```mermaid
flowchart LR
    Edit["CLI・直接編集"] --> Serve["サーバー<br/>読み直しと比較"]
    Serve -->|"SSE changed"| Core["ブラウザのデータ層"]
    Core -->|"GET summary"| Serve
    Core -->|"GET detail（NDJSON）"| Serve
```

### 変更から画面まで

通知にデータそのものは含まれません。通知が伝えるのは、変わったものの名前だけです。ブラウザは必要なものを読み、結果をキャッシュに保持します。

```mermaid
flowchart LR
    Files[("共有ファイル")] --> Index["索引の投影<br/>Summaryとversion"]
    Index --> Cache[("ブラウザのキャッシュ<br/>Summary・Detail")]
    Cache --> Screen["ボード・モニター・<br/>詳細パネル"]
```

- **Summary。** カードと一覧の行はすべてプロジェクトのSummaryから描きます。Summaryは本文を含まないので、ボードは速く表示され、1つのタスクが変わっても、ほかのタスクの本文は読み直しません。
- **Detail。** 本文・完了条件の文章・履歴は、カードやエピックを開いたときだけ読みます。ブラウザは、セクションごとにversionを付けて保持します。
- **SSE。** 1つの`changed`イベントは、変わったタスク・エピック・項目を、`instanceId`と`seq`とともに知らせます。`seq`の欠番や新しい`instanceId`は、ブラウザがキャッシュを捨ててSummaryを読み直す合図です。
- **キャッシュ。** ブラウザは、直近4プロジェクトのSummaryと、上限のある数のDetailを、最も長く使われていないものから捨てながら保持します。通知だけでキャッシュを書き換えることはなく、ブラウザは必ずデータを読み直します。

### リモートアクセス

スマホのブラウザは、`serve`の中で動くngrokのトンネルを通して、読み取り中心のモニターに接続します。接続は**設定**か`agboard serve --monitor ngrok`で始め、公開Hostの完全一致と、起動ごとに作る4桁の合言葉で守ります。トンネルの転送先は専用のループバックの入口です。その入口は、ローカルと同じFileStore・ファイル監視・更新通知を使います。詳しくは[リモートアクセス](./remote-access.md)を参照してください。

```mermaid
flowchart LR
    Browser["スマホのブラウザ"] --> Tunnel["ngrok<br/>トンネル"]
    Tunnel --> Entry["モニターの<br/>入口"]
    Entry --> Shared["FileStore"]
```

### プロジェクトのドキュメント

各プロジェクトには、利用者の文書を置く`docs/`もあります。プロジェクトのフォルダの中にありますが、ボードとは切り離して扱います。`version`には含めず、変化があったときは`changed`ではなくSSEの`docs`イベントを送ります。ブラウザは専用のルートでファイルを読むだけで、編集は利用者のエディタで行います。[変更の通知](./notifications.md#ドキュメント)と[セキュリティモデル](./security.md#プロジェクトのドキュメント)を参照してください。

```mermaid
flowchart LR
    Browser["ドキュメントのダイアログ"] <--> Routes["ドキュメントのルート"]
    Routes <--> Docs[("docs/フォルダ")]
    Others["エディタ・git・エージェント"] --> Docs
```

### 基本方針

設計の基本方針は次の三つです。

- **すべての操作は対象のプロジェクトを指定する。** プロジェクトは不変なProjectIdで識別し、コマンドが作業フォルダや選択から対象を推測することはありません。フォルダの紐付けは、Hookが正しいプロジェクトを見つけるためだけにあります。
- **タスクは一組で保存する。** `task.json`（状態）と`TASK.md`（本文・条件・履歴）はロックの中で一緒に確定するので、片方だけが見えることはありません。[保存と復旧](./saving-and-recovery.md)を参照してください。
- **ファイルを正本とし、サーバーはキャッシュを持つ。** `serve`は高速な読み取りのためにメモリ上の索引を保持しますが、データの正本はファイルです。サーバーが止まっていてもCLIは動き、起動し直せばファイルを読み込みます。サーバーが要るコマンド（待つコマンドや、答えを待つ質問）はサーバーを起動し、こうして起動したサーバーは使われなくなると自分で止まります。

## 一つの変更を追う

### エージェントがタスクを移動する

エージェントが`agboard --project demo mv 12 doing --actor ai`を実行すると、次のように進みます。

1. CLIがプロジェクト名をProjectIdに解決します。
2. プロジェクトの書き込みロック（`.internal/write.lock`）を最大5秒待って取ります。
3. ロックの中で最新の`task.json`と`TASK.md`を読み直し、規則（例えば、未達成の条件があるのにAIがDoneへ移せないこと）を確かめ、更新後の状態と履歴を組み立てます。
4. ジャーナルを使って両ファイルを一組で保存し、ロックを解放します。
5. 実際に何かが変わっていれば、`serve.json`を読んで、稼働中のサーバーに`POST /api/notify`を送ります。サーバーが動いていなくても問題ありません。
6. サーバーはプロジェクトを読み直し、データが変わったことを確かめて、変わったタスクと項目を添えてSSEの`changed`をすべてのブラウザに送ります。各ブラウザは、プロジェクトのSummaryを読み直し、開いている詳細のうち変わったものだけを読み直します。

### 人がブラウザで質問に答える

1. ブラウザが`POST /api/projects/{projectId}/qa/answers`に、質問IDと選んだ選択肢、ページに埋め込まれた書き込み用トークンを付けて送ります。
2. サーバーはタスクを探すより前に、Host・Origin・`Sec-Fetch-Site`・トークンを確かめます。
3. 書き込みロックの中で、質問がまだ未回答であることを確かめ、回答を`qa/<request-id>/request.json`に保存し、質問を参照する各タスクに履歴を追加して、これらのファイルを一つの変更として確定します。
4. versionが変わり、ブラウザはSSEで更新されます。待っている`qa ask`や`qa wait`のコマンドは同じSSEで起きてリクエストを読み、全問に回答が揃うと回答を出して終わります。`--no-wait`は保存と通知の後に戻ります。

### エージェントがTASK.mdを直接編集する

1. エディターがファイルを書きます。直接編集にはロックが適用されず、後から保存した内容で上書きされます。
2. サーバーのファイル監視がOSのイベントを受け取り、関連するイベントを200msの間に集約します。
3. プロジェクトを読み直し、条件を満たしたタスクの自動Doneを評価し、データが変わっていればブラウザと待機中のエージェントに知らせます。
