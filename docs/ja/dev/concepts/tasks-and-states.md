# タスクと状態

プロジェクトとタスクの構造、有効なレーンと稼働状態の組み合わせ、エピック・下書き・アーカイブとの関係を説明します。各項目の詳細は[共有ファイル](../reference/files.md)にあります。

## プロジェクト

プロジェクトは、名前と不変な**ProjectId**（作成時に生成する32桁の小文字16進文字列）を持つ作業単位です。各プロジェクトはボードを一つだけ持ちます。プロジェクト横断のボードや、プロジェクト間のタスクの移動・コピーはありません。

- 名前は前後の空白を除いて1〜50 Unicodeスカラー値、1行で、大文字・小文字を区別した完全一致で一意です。プロジェクト一覧は名前順です。
- 名前変更と`init`ではProjectIdは変わりません。削除したProjectIdは再利用しないので、同じ名前で作り直したプロジェクトは別のプロジェクトです。
- タスクID・レーン内のposition・EPIC-IDはプロジェクト内の値です。対象のプロジェクトを、省略・作業フォルダ・Webの選択から推測しません。
- `nextTaskId`は1から始まり、削除や`init`の後もリセットされず、増え続けます。作成に失敗した場合も、予約済みの番号は再利用しません。
- `init`はID・名前・`nextTaskId`を保ち、タスクとエピックを空にします。プロジェクトの削除はそのフォルダ全体を消し、ほかのプロジェクトには触れません。

変更の検知には三つの値を使います。`version`は1プロジェクトの正本ファイルから計算し、順序を持ちません。`catalogVersion`は、同じ方法でプロジェクト一覧の変更を識別します。`cursor`（`f1:<ProjectId>:<version>`）は`wait`が使う値で、名前変更後も同じProjectIdを追い、別のプロジェクトへは移りません。

## レーンと稼働状態

レーンは作業がどこにあるかを、稼働状態はエージェントがそれに対して何をしているかを表します。有効な組み合わせは限られます。

| 担当 | レーン | 有効な稼働状態 |
| --- | --- | --- |
| ai | todo | idle、pending |
| ai | doing | idle、running、pending |
| ai | done | idleのみ |
| human | すべて | idleのみ |

- **Running**は自己申告で、生存監視ではありません。自動で戻ることはなく、エージェントもセッションの開始や中断だけを理由に変えません。
- **Pending**はエージェントが人の判断を待っている状態です。その間もほかのタスクを進めてかまいません。
- 無効な組み合わせは保存しません。下書きのタスクは、どのレーンでもIdleかPendingです。

操作によって状態は次のように変わります。

- **作成**はタスクをTodo・Idleでレーンの末尾に置き、作成を履歴に記録します。本文がなければ空の`acceptance`と空の本文を書き、指定した本文はfrontmatterの検証を通します。
- **列移動**は`actor`が必須で、`reason`は任意です。タスクは移動先のレーンの末尾に置きます。実際の移動では稼働状態をIdleに戻し、未回答の依頼を取り下げ（取り下げは回答ではありません）、履歴を追加し、`taskStatusChangedAt`を更新します。同じレーンへの移動は何も変えません。
- **稼働状態の変更**は`actor`が必須で、レーンは変わりません。AI担当のTodoはIdle↔Pending、AI担当のDoingはIdle・Running・Pendingの間の変更を受け付けます。同じ状態の再申告は変更ではありません。
- **編集**で変わるのはタイトル・本文・受入条件だけで、担当は変わりません。CLIの`--desc`・`--desc-file`はファイル全体を受け取りますが、保存済みの最新の`TASK.md`の履歴を保ちます。`epic edit --plan-file`は`PLAN.md`全体を置き換えます。Web画面は`body`と`acceptance`を送り、ロックの中で最新のファイルに適用します。
- **エピックの所属**は`epicId`を設定または解除します。実際に変わったときだけ履歴を追加します。下書きやアーカイブ済みのタスクでも人は変更できます。
- **削除**はタスクのフォルダを消します。Web画面はアーカイブ済みのタスクだけを削除し、CLIは端末での確認を求めます。

通常の更新では、後から保存した内容が優先され、内容の照合や編集ロックはありません。最新の`task.json`と照らして書き込みロックの中で検証するのは、回答の照合、下書きへのAIの書き込み、アーカイブ済みへの書き込み、一括アーカイブの対象だけです。

## エピックと進行順

エピックはタスクをまとめる計画（`PLAN.md`）です。タスクは最大で一つのエピックに所属できます。

| 項目 | 規則 |
| --- | --- |
| `id` | EPIC-ID。`[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*`に合う1〜64文字。小文字の入力は大文字にする。変更不可。 |
| `name` | 前後の空白を除いて1〜100文字、1行。 |
| `color` | `#RRGGBB`（大文字）。省略時は作成時に乱数で決める。 |
| `isDraft` | 準備中の計画の印。所属タスクには影響しない。 |
| `plan`・`body` | `PLAN.md`の全文（0〜50,000文字）と、frontmatterを除いた本文。 |
| `priority`・`priorityError` | 所属タスクIDの作業順と、その読み込みに失敗したかどうか。 |

- タスクは`epicId`だけを保存し、ラベルの色と名前は取得時に解決します。
- アーカイブ済みを含め、いずれかのタスクが参照しているエピックは削除できません（`epic_in_use`）。
- エピックには管理対象の受入条件はありません。参考条件は本文の通常のMarkdownで、APIはエピックへの`acceptance`の入力を拒否します。
- `priority`は`PLAN.md`のfrontmatterにあるタスクIDのリストで、例えば`priority: [24, 26, 25]`です。重複や型の誤りは保存時のエラーです。所属しなくなったIDは表示から除き、次の保存で取り除きます。記載のない所属タスクは作成順で後に続きます。進行順の変更はDoneのタスクの編集に当たりません。レーン内の`position`は、エピックの作業順序には影響しません。

## 下書き

下書きは、人がまだ書いているタスクです。

- 人がWeb画面で`isDraft`を切り替えます。下書きにできるのはIdleかPendingのタスクだけで、Runningは拒否します。実際に変わると履歴を追加しますが、`updatedAt`は変えません。
- CLIの`edit`・`mv`・`state`・`history add`は、書き込みロックの中で`isDraft`を確かめ、`task_is_draft`で失敗します。読み取り・`add`・人によるWebの操作は影響を受けません。時間の経過によって下書きが自動で確定されることはありません。
- Webの編集は下書きのタスクだけを受け付けます。`finalize`を指定すると、本文・タイトル・`isDraft=false`・履歴を一組で確定します。
- 下書きの`TASK.md`の直接編集は製品では止められず、READMEとエージェントのスキルで編集しないよう伝えます。

## アーカイブ

- アーカイブでは、レーン・`isDraft`・`epicId`・positionを保ち、稼働状態をIdleに戻し、依頼を取り下げ、`updatedAt`を更新します。レーンと`taskStatusChangedAt`は変わりません。Web画面のアーカイブと復元は、固定の理由`Archived by user.`と`Restored by user.`を記録します。
- 復元したタスクは元のレーンの末尾に置きます。
- 通常のスナップショット・`ls`・Hookは未アーカイブのタスクだけを返し、`show ID`はアーカイブ済みも表示します。アーカイブ済みへの書き込みは`task_archived`で失敗しますが、画像と証跡は読めます。アーカイブ一覧は`archivedAt`の新しい順です。

## 並び順と日時

- PCのボードとCLIでは、TodoとDoingはpositionの昇順、Doneはpositionの降順です。モバイルのDone一覧は`taskStatusChangedAt`の新しい順です。完了順を履歴から推測しません。APIの`tasks`はID順で、画面が表示用に並べ替えます。エピックはEPIC-ID順です。
- 保存とJSONの日時は、厳密に`YYYY-MM-DDTHH:MM:SSZ`の形のUTC文字列です。時差表記（`+00:00`も）と小数秒は拒否します。表示は`MM/DD HH:mm`で、CLIは実行環境、画面はブラウザのローカル時刻を使います。
