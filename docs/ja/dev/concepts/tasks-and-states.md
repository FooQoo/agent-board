# タスクと状態

プロジェクトとタスクの構造、有効なレーンと稼働状態の組み合わせ、エピック・下書き・アーカイブとの関係を説明します。各項目の詳細は[共有ファイル](../reference/files.md)にあります。

## プロジェクト

プロジェクトは、名前と不変な**ProjectId**（作成時に生成する32桁の小文字16進文字列）を持つ作業単位です。各プロジェクトはボードを一つだけ持ちます。プロジェクト横断のボードや、プロジェクト間のタスクの移動・コピーはありません。

- 名前は前後の空白を除いて1〜50 Unicodeスカラー値、1行で、大文字・小文字を区別した完全一致で一意です。プロジェクト一覧は名前順です。
- 名前変更と`init`ではProjectIdは変わりません。削除したProjectIdは再利用しないので、同じ名前で作り直したプロジェクトは別のプロジェクトです。
- タスクID・レーン内のposition・EPIC-IDはプロジェクト内の値です。対象のプロジェクトを、省略・作業フォルダ・Webの選択から推測しません。
- `nextTaskId`は1から始まり、削除や`init`の後もリセットされず、増え続けます。作成に失敗した場合も、予約済みの番号は再利用しません。
- `init`はID・名前・`nextTaskId`を保ち、タスクとエピックを空にします。プロジェクトの削除はそのフォルダ全体を消し、ほかのプロジェクトには触れません。

変更の検知には三つの値を使います。`version`は1プロジェクトの正本ファイルから計算し、順序を持ちません。`catalogVersion`は、同じ方法でプロジェクト一覧の変更を識別します。`cursor`（`f1:<ProjectId>:<version>`）は`wait`が使う値で、名前変更後も同じProjectIdを追い、別のプロジェクトへは移りません。

## レーンと稼働状態

レーンは作業がどこにあるかを、稼働状態はエージェントがそれに対して何をしているかを表します。有効な組み合わせは限られます。

| 担当 | レーン | 有効な稼働状態 |
| --- | --- | --- |
| ai | backlog | idleのみ |
| ai | todo | idle、pending |
| ai | doing | idle、running、pending |
| ai | done | idleのみ |
| human | すべて（backlogを含む） | idleのみ |

- **Running**は自己申告で、生存監視ではありません。自動で戻ることはなく、エージェントもセッションの開始や中断だけを理由に変えません。
- **Pending**は、タスクが参照するプロジェクトの質問に、まだ回答がない状態です。読めないメッセージのファイルを参照しているタスクもPendingです。その間もほかのタスクを進めてかまいません。Pendingは保存しません。`task.json`にはIdleかRunningを保存し、読み出すときにタスクの`questions`からPendingを導きます（[メッセージ](./history-and-decisions.md#メッセージ)）。
- 無効な組み合わせは保存しません。下書きのタスクは、どのレーンでもIdleかPendingです。

操作によって状態は次のように変わります。

- **作成**はタスクをTodo・Idleでレーンの末尾に置き、作成を履歴に記録します。本文がなければ空の`acceptance`と空の本文を書き、指定した本文はfrontmatterの検証を通します。
- **列移動**は`actor`が必須で、`reason`は任意です。タスクは移動先のレーンの末尾に置きます。実際の移動では保存した稼働状態をIdleに戻し、履歴を追加し、`taskStatusChangedAt`を更新します。同じレーンへの移動は何も変えません。
- **稼働状態の変更**は`actor`が必須で、レーンは変わりません。`state`が受け付けるのはIdleとRunningで、RunningにできるのはAI担当のDoingだけです。回答待ちのタスクをAIがRunningにしようとすると`questions_unanswered`で拒否します。質問は`message ask`で出し、そのときRunningのタスクはIdleに戻ります。列移動やアーカイブをしても、タスクの質問と参照は残ります。同じ状態の再申告は変更ではありません。
- **編集**で変わるのはタイトル・本文・完了条件だけで、担当は変わりません。CLIの`--desc`・`--desc-file`はファイル全体を受け取りますが、保存済みの最新の`TASK.md`の履歴と`questions`の参照を保ちます。入力のこの2つのキーは無視されるため、未回答の質問を参照するタスクは保留のままです。`epic edit --document-file`は`EPIC.md`の全文を置き換えます。Web画面は`body`と`acceptance`を送り、ロックの中で最新のファイルに適用します。
- **エピックの所属**は`epicId`を設定または解除します。実際に変わったときだけ履歴を追加します。下書きやアーカイブ済みのタスクでも人は変更できます。
- **削除**はタスクのフォルダを消します。Web画面はアーカイブ済みのタスクだけを削除し、CLIは端末での確認を求めます。

通常の更新では、後から保存した内容が優先され、内容の照合や編集ロックはありません。最新の`task.json`と照らして書き込みロックの中で検証するのは、回答、人の下書きへのAIの書き込み、アーカイブ済みへの書き込み、一括アーカイブの対象だけです。

## エピックとウェーブ

エピックは、タスクをまとめて進行と作業順を管理する単位です。エピックの詳細（`EPIC.md`）には、目的・範囲・判断などをMarkdownで書きます。タスクは最大で一つのエピックに所属でき、所属の正本はタスクの`epicId`だけです。エピック側はタスクの一覧を保存しません。

| 項目 | 規則 |
| --- | --- |
| `id` | EPIC-ID。`[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)*`に合う1〜64文字。小文字の入力は大文字にする。変更不可。 |
| `name` | 前後の空白を除いて1〜100文字、1行。 |
| `color` | `#RRGGBB`（大文字）。省略時は作成時に乱数で決める。 |
| `draft` | タスクと同じく`null`または`"human"`。人の下書き（`human`）のエピックは、CLIの`epic edit`と`--waves`を`epic_is_draft`で拒否する。所属タスクと`epic attachment`には影響しない。エピックにレーンはなく、`progress`には任意の`backlog`の件数がある。 |
| `document`・`body` | frontmatterを含む`EPIC.md`の全文（0〜100,000文字）と、frontmatterを除いた本文。 |
| `waves`・`wavesError` | 所属タスクの作業順をウェーブ（タスクIDのリストのリスト）で表したものと、保存された順序の読み込みに失敗したかどうか。 |

- タスクは`epicId`だけを保存し、ラベルの色と名前は取得時に解決します。
- アーカイブ済みを含め、いずれかのタスクが参照しているエピックは削除できません（`epic_in_use`）。Web画面ではエピックの編集画面から`DELETE .../epics/{epicId}`で削除します。CLIでは`epic rm`を使います。
- 新しいプロジェクトには、既定のエピック`BUG`と`ENHANCEMENT`が最初からあります。どちらも通常のエピックなので、編集も削除もできます。プロジェクトにこれらを用意し終えると`project.json`の`defaultEpicsSeeded`が設定されるので、削除した既定のエピックが作り直されることはありません。`serve`は、このフラグがまだないプロジェクトに一度だけ用意します。
- エピックには管理対象の完了条件はありません。参考条件は本文の通常のMarkdownで、APIはエピックへの`acceptance`の入力を拒否します。
- `waves`は`EPIC.md`のfrontmatterにあるYAMLのリストで、各項目が1つのウェーブです。項目はタスクID（`24`）、またはカンマでつないだタスクID（`26,25`。カンマの後の空白と引用符は許容）です。入れ子のリストは受け付けません。ウェーブをまたぐ重複、正でないID、空の項目、型の誤りはエラーです。保存時は、空のウェーブを取り除きます。所属しなくなったIDは表示から除き、次の保存で取り除き、空になったウェーブも取り除きます。記載のない所属タスクは作成順で後に続きます。ウェーブの変更はDoneのタスクの編集に当たりません。レーン内の`position`は、エピックの作業順序には影響しません。
- ウェーブは、その前のウェーブのタスクがすべてDoneになってから始まります。`nextTasks`は、同じエピックの前のウェーブに、アーカイブされておらずDoneでないタスクが残っている間、そのTodoのタスクを載せません。アーカイブしたタスクは無視し、どのウェーブにも載らないタスクは待たされず、順序を読めないときは何も止めません。止まっているDoingの作業は、これまでどおり`resume`として載ります。

## 下書き

下書きは、人がまだ書いているタスクやエピックです。`draft`は`null`（通常のタスク）か`"human"`（人がブラウザで書いている。編集ロック）です。保存される項目は[共有ファイル](../reference/files.md)にあります。下書きに期限はなく、`wait`と自動Doneはすべての下書きを飛ばします。AIの下書きはありません。エージェントが提案する計画はBacklogのタスクです（[Backlogと送信](#backlogと送信)を参照）。

- エージェントが作ったタスクとエピック（CLIの`add`と`epic add`）は`draft: null`です。人が作ったものは`null`で、ブラウザで下書きとして作ると`human`です。
- プレビューは、最初の実際の変更で人の下書きに入ります。タスクは`PUT /tasks/{id}/draft`で`draft: "human"`を送り、エピックは`PATCH /epics/{id}`で`draft: "human"`を送ります。下書きにできるのはIdleまたはPendingのタスクだけで、Runningは`invalid_state_for_draft`で拒否します。実際の変更は履歴を追加しますが、`updatedAt`は変えません。エピックの下書きに入る・出るときも`updatedAt`は変わりません。古いバージョンのクライアントが送る`draft: "ai"`は受け付け、`null`として扱います（編集ロックを解除します）。`draft: "ai"`でのタスクの作成は拒否します。
- `human`の下書きでは、CLIの`edit`・`mv`・`state`・`history add`が書き込みロックの中で`draft`を確かめ、`task_is_draft`で失敗し、CLIの`epic edit`と`epic edit --waves`は`epic_is_draft`で失敗します。読み取り、`add`、`epic attachment`、所属の変更には影響しません。エピックへのWebの`PATCH`は下書きを拒否しません。
- Webの編集は下書きのタスクだけを受け付けます。`finalize`を指定すると、本文・タイトル・`draft: null`・履歴を一組で確定します。破棄は、`draft: null`と`discard: true`を送り、履歴に`Discarded draft changes.`を残します。エピックに履歴はないので、破棄は`PATCH /epics/{id}`の`draft: null`だけです。
- 下書きの`TASK.md`の直接編集は製品では止められず、READMEとエージェントのスキルで編集しないよう伝えます。

## Backlogと送信

Backlogのレーンは、まだ始めてはいけない確定済みの計画を置く場所で、「始めない」と同じ意味です。計画はチャットやAIへの依頼で直します。Backlog専用の編集はなく、通常のカードの編集は変わりません。Backlogを使うファイルは`formatVersion: 2`になります（[保存と復旧](./saving-and-recovery.md#形式のバージョンとbacklogへの移行)を参照）。

- **作成。** `agboard add ... --actor ai --backlog`でBacklogにカードを作ります。エージェントは、計画だけを頼まれたときに使います。`--backlog`なしのエージェントの`add`は、通常のTodoのタスクを作ります（未回答の質問があればこれまでどおりPendingになります）。`epic add`にレーンはありません。エージェントのエピックは通常のエピックで、計画だけのエピックは、カードを`--backlog --epic <ID>`で作ったものです。
- **送信。** BacklogからTodoへ送れるのは人だけです。`agboard send <id> --actor human [--force]`と、エピック全体または選んだカードを、全部成功か何も変えないかの一回の保存で送る`agboard epic send <EPIC-ID> --actor human [--tasks 1,2] [--force]`です。Webのルートは`POST /tasks/{id}/send`と`POST /epics/{epicId}/send`（[Web API](../reference/web-api.md)を参照）で、WebのUIではBacklogのレーン、カードの詳細、エピックの詳細から送れます（[サーバーとUI](./server-and-ui.md)を参照）。エージェントが行うと`human_only`になります。`agboard start`と`agboard epic start`は、同じ動作の非推奨の隠しエイリアスとして残っています。Todoへ送ったカードはTodoの末尾に置かれ、すでにBacklogを出たカードを送っても何も変わらないので、再試行しても安全です。人が編集中のカード（`draft: human`）は送れません（`task_is_draft`）。履歴には`人が Todo へ送りました。`と残ります。
- **未回答の質問。** 未回答の質問がある計画は、人が`--force`（CLI）または`ack: true`（API）で確認するまで、`send_with_open_questions`（409。メッセージに質問のIDを示す）で拒否します。送ったあとも質問は残り、回答があるまでカードはPendingです。
- **移動。** エージェントのBacklogのカードへの`mv`・`state`は`task_in_backlog`で失敗します。人のWebでのTodoへの移動は`ack`なしの送信で、DoingやDoneへの移動は`task_in_backlog`です。`agboard mv <id> backlog --actor human`は、未着手のTodoのカード（Idleで成果なし）をBacklogへ戻します。エージェントが行うと`human_only`です。
- **エージェントの画面。** nextTasks・`wait`・Hook・常駐セッション・自動Done・進捗表の候補は、Backlogを見ません。エピックの中のBacklogのカードは、Doneではないので、あとのウェーブを待たせ続けます。エピックの`progress`には、任意の`backlog`の件数があり、0のときは省きます。
- **規則の置き場所。** 送信の規則は`src/file_store/ops/send.rs`にあり、`check_sender`と`open_questions`が、タスク、またはエピックの送信が動かすすべてのカードについて、エージェントと、確認のない未回答の質問のある計画を拒みます。
- 下書きの`TASK.md`の直接編集は製品では止められず、READMEとエージェントのスキルで編集しないよう伝えます。

## アーカイブ

- アーカイブでは、レーン・`draft`・`epicId`・positionを保ち、保存した稼働状態をIdleに戻し、質問の参照を保ち、`updatedAt`を更新します。レーンと`taskStatusChangedAt`は変わりません。Web画面のアーカイブと復元は、固定の理由`Archived by user.`と`Restored by user.`を記録します。
- 復元したタスクは、アーカイブしたときのレーンの末尾に、稼働状態Idleで置きます。アーカイブでは必ずIdleを保存するので、復元したタスクはアーカイブ時点の稼働状態になり、レーンとIdleの組み合わせは常に作業モデルで有効です。フォールバックは要りません。スマホのアーカイブ一覧も、PCと同じ`POST …/tasks/{id}/restore`で復元します。
- 通常のスナップショット・`ls`・Hookは未アーカイブのタスクだけを返し、`show ID`はアーカイブ済みも表示します。アーカイブ済みへの書き込みは`task_archived`で失敗しますが、画像は読めます。アーカイブ一覧は`archivedAt`の新しい順です。

## 並び順と日時

- PCのボードとCLIでは、TodoとDoingはpositionの昇順、Doneはpositionの降順です。モバイルのDone一覧は`taskStatusChangedAt`の新しい順です。完了順を履歴から推測しません。APIの`tasks`はID順で、画面が表示用に並べ替えます。エピックはEPIC-ID順です。
- 保存とJSONの日時は、厳密に`YYYY-MM-DDTHH:MM:SSZ`の形のUTC文字列です。時差表記（`+00:00`も）と小数秒は拒否します。表示は`MM/DD HH:mm`で、CLIは実行環境、画面はブラウザのローカル時刻を使います。
